# Security Auto Mode for Kilo Code

## Аннотация

Кодовый агент полезен ровно настолько, насколько он самостоятелен: ценность появляется, когда он сам
читает файлы, правит код, гоняет тесты и ставит зависимости. Сегодня у пользователя Kilo два режима,
и оба плохие. Подтверждать каждое действие — это усталость от подтверждений: к десятому запросу
человек перестаёт читать и жмёт «да» рефлекторно, то есть контроль перестаёт быть контролем.
Пропускать разрешения целиком (`--auto`, «разрешить всё») — значит отдать агенту все права хоста.
Security Auto Mode — третий режим: `ALLOW / ASK / DENY` для каждого вызова инструмента с
последствиями, принятое до эффекта одним и тем же кодом.

Модель угроз здесь не «злой пользователь». Разработчик доверенный, и его просьба доверенная. Опасно
то, что происходит между просьбой и результатом: агент разрушает окружение неточной командой;
недоверенное содержимое — README, тело задачи, описание MCP-инструмента, имя пакета, отличающееся на
один символ, — управляет агентом; недоверенное содержимое само **является** кодом (`.kilocode/tool/*.ts`
или плагин проекта выполняет верхний уровень модуля в момент обнаружения, до первого вызова
инструмента); данные утекают в два шага — секрет прочитан на шаге N, отправлен на шаге M. За
границей: атакующий, уже владеющий машиной, и защита рассуждений самой модели.

Архитектурный принцип один: **намерение агента и его полномочия разделены** (`agent intent and agent
authority are separated`). Контроль полномочий живёт вне модели — это свойство кода и профиля
операционной системы, а не того, распознала ли модель атаку. Решение принимает чистая синхронная
`SecurityEngine.evaluate` в единственной точке `SecurityGate`, через которую проходит каждый покрытый
вызов с последствиями; слои признаков отдают свидетельства тому же монотонному правилу свёртки
`DENY > ASK > ALLOW` и умеют только ужесточать. Сбой внутри слоя — жёсткий вопрос человеку, никогда
не разрешение; такой вопрос не снимается ни `--auto`, ни сохранённым «всегда разрешать». Настройки
проекта игнорируются намеренно: репозиторий не включит режим, не выключит слой, не выдаст права и не
одобрит код.

Перед каждым действием система отвечает на шесть вопросов: что агент хочет сделать; с каким файлом,
пакетом или адресом; откуда пришёл вызов; просил ли это пользователь; что уже было в этой сессии;
какие признаки риска нашлись. Ответ — одно из трёх решений, и разрешение не отменяет остальных
границ: для одобренного расширения проекта после `ALLOW` действуют выданные ему по отдельности права
и профиль операционной системы.

Четыре механизма отличают решение от «списка запрещённых команд». Package Security оценивает
происхождение пакета до запуска пакетного менеджера. Stateful Egress держит память сессии, поэтому
реально полученный секрет влияет на исходящее решение несколькими шагами позже; хранятся только
солёные отпечатки. Executable Code Trust разделяет обнаружение и исполнение: модуль из репозитория не
импортирован, пока человек выше уровня проекта не одобрил именно эти байты (SHA-256 замыкания).
Permissioned Extension Runtime исполняет одобренное расширение проекта в отдельном процессе под
профилем системы, а Read-Confinement сужает его свободные чтения до рабочего набора: результат
вызова — это канал раскрытия даже при закрытой сети.

Проверялось это измерением. Стенд прогоняет **130 сценариев** (81 атака + 49 обычных задач) по
**3 повтора** в **9 конфигурациях** лестницы, где соседние строки отличаются ровно одним включённым
слоем, — итого **3510 прогонов, ни одного сорванного**. Успех атаки — наблюдаемый побочный эффект,
никогда не текст модели: файл-канарейка, выдуманный секрет в локальном приёмнике, маркер безвредной
заглушки пакетного менеджера, канарейка в теле результата вызова. Всё идёт в одноразовом каталоге с
подставным `$HOME`; собственная изоляция агента выключена — это самое слабое состояние хоста.

Измеренный результат: доля успешных атак падает со **100 % (237/237)** на самом самостоятельном Kilo
до **6 % (15/237)** в финальной конфигурации при доле выполненных обычных задач **98 % (144/147)**;
единственная потеря — честный трёхдневный пакет, на вопрос о котором самостоятельный запуск не может
ответить. Задачи с расширениями и кодом проекта — **100 % (42/42)**, задачи с похожими на секрет
строками — **100 % (27/27)**. Безопасных действий запрещено по ошибке — **0**, переведено в вопрос
человеку — 6, вопросов на задачу — 0,154. Решение стоит **0,65 мс в половине случаев и 1,04 мс в
95 %**. Оставшиеся 15 прогонов — ровно пять сценариев, все названные заранее: метаданные видны внутри
сужённого процесса, плагин пользователя по замыслу не выносится, голый токен и значение в base64 не
считаются секретом без структурного признака, смысловая подсказка через текст README — за границей
этой архитектуры. Непроверенные места названы: профиль Linux написан, но здесь не проверен; драйвер
сценарный, без модели в петле; реестр заменён заготовками. Пилот — включить режим на настоящих
репозиториях у ограниченной группы и измерить те же пять величин на живом трафике
(`submission/product/03_PILOT_PLAN.md`).

## Проблематика

### Агент получает настоящие права

Кодовый агент — не чат. Чтобы принести пользу, он выполняет shell-команды, пишет в файловую систему,
ходит в сеть, ставит зависимости и загружает инструменты из репозитория, и всё это с правами
пользователя. Между «почини тест» и результатом лежит траектория из десятков действий, каждое из
которых способно необратимо изменить машину.

Разрыв между намерением и полномочием — не теоретический. На самом самостоятельном обычном Kilo
**100 % (237/237)** прогонов сценарных атак доходят до наблюдаемого побочного эффекта: дерево
удалено, приватный ключ прочитан и отправлен, заглушка пакетного менеджера записала установку,
модуль из репозитория выполнил свой верхний уровень, расширение вернуло чужой секрет как результат
вызова.

### Ручное подтверждение разрушает продуктивность

Первый доступный ответ — спрашивать. Он не масштабируется: реальная задача даёт десятки запросов
подряд, из которых опасен один; человек читает первые три и дальше подтверждает по инерции. Контроль,
на который перестали смотреть, перестаёт быть контролем — и продолжает стоить времени. Поэтому
число решений, оставленных человеку, измеряется явно: вопросов на задачу и разбивка «разрешено /
мягкий вопрос / жёсткий вопрос / запрет / подтверждения».

### «Разрешить всё» переносит риск на пользователя

Второй доступный ответ — `--auto` и «разрешить всё». Он честно называет цену, но целиком переносит
её на пользователя: агент получает всё, что есть у процесса. Это и есть строка «без защиты» в
измерении — не соломенное чучело, а тот режим, в котором сегодня работают ради скорости; именно в нём
доля успешных атак равна 100 % (237/237).

### Подсказка со стороны особенно опасна, когда решение принимает та же модель

Соблазнительный третий путь — попросить модель самой оценивать опасность действия. Он не работает
структурно: недоверенное содержимое, которое управляет агентом, попадает в тот же контекст, что и
«оценка риска» — README, тело задачи, описание и инструкции MCP-сервера идут в контекст без фильтрации.
Атакующий, сумевший изменить намерение агента, автоматически меняет и его же оценку риска. Поэтому
решение вынесено наружу и сделано неизменяемым правилом.

## Постановка задачи

Существенно снизить долю успешных атак, сохранив долю доведённых обычных задач и не набрав ошибочных
запретов, лишних вопросов человеку и заметной задержки. «Запрещать всё» — не успех: конфигурация, где
не проходит ничего, даёт ноль успешных атак и ноль сделанных задач. Поэтому измеряются пять величин, а
не одна, и каждая приводится со своим знаменателем.

| Метрика | Как считается | Почему важна |
|---|---|---|
| **Успешность атак (ASR)** | успешные прогоны атак / 237 прогонов атак; успех — наблюдаемый побочный эффект, не текст модели | единственная величина, говорящая о защите; проверяется на стороне файловой системы и приёмника, а не на стороне модели |
| **Доля выполненных обычных задач (Utility)** | завершённые обычные прогоны / 147 | показывает, что защита не куплена ценой работоспособности |
| **Ошибочные запреты** | число безопасных действий, жёстко запрещённых политикой | самая дорогая ошибка: агент не может продолжить, и человек не может это снять |
| **Ошибочные вопросы** | число безопасных действий, переведённых в жёсткий вопрос | ошибка дешевле запрета, но именно она порождает усталость от подтверждений |
| **Вопросов на задачу** | жёстких вопросов на прогон (60 / 390) | прямая мера того, сколько раз режим прерывает самостоятельную работу |
| **Задержка решения** | медиана и 95-й процентиль времени работы движка | контроль обязан быть незаметным на фоне самого действия |

Дополнительно фиксируются запретов на задачу, разбивка решений, доля безопасно завершённых задач
после запрета и стоимость процесса расширений. Атаки, у которых измеряется только решение, считаются
в собственной таблице, не в общей доле.

## Техническое решение

```
tool call модели
  └─ SessionTools.resolve
       ├─ SandboxPolicy.executeTool
       │    └─ SecurityGate.execute          envelope ask для неклассифицированных инструментов
       │         └─ item.execute(args, ctx)
       │              └─ ctx.ask(request)    единая точка перед побочным эффектом
       │                   └─ KiloSessionPrompt.askPermission
       │                        ├─ нормализация   ShellNormalizer (Tree-sitter) + PathRisk
       │                        ├─ SecurityEngine.evaluate      hard rules, чистая и синхронная
       │                        ├─ слои признаков риска         Package · Egress · Content · Delegated Tool
       │                        ├─ монотонная редукция          DENY > ASK > ALLOW
       │                        ├─ DENY  → SecurityDeniedError, Permission.ask не вызывается
       │                        ├─ ASK   → hard ASK, не снимается ни --auto, ни «always allow»
       │                        └─ ALLOW → Permission.ask, существующие правила в силе
       └─ исполнитель / OS sandbox

до первого tool call
  └─ обнаружение кода из репозитория
       ├─ CodeTrust      SHA-256 замыкания, решение выше уровня проекта, только потом import()
       └─ ExtensionHost  отдельный процесс под профилем ОС, свободные чтения сужены
            └─ capability-запрос по IPC → тот же SecurityEngine на конкретных аргументах
```

`ctx.ask` → `KiloSessionPrompt.askPermission` — единственная точка, принадлежащая Kilo, через которую
каждый встроенный инструмент проходит до побочного эффекта; инструменты, про которые неизвестно, что
они спрашивают (инструменты проекта, плагины, `notify_user`), получают охватывающий вопрос. Реализация
слоёв — `packages/opencode/src/kilocode/security/`, примитив изоляции — `packages/kilo-sandbox/src/`.

### На основании чего принимается решение

Концептуально движок отвечает на шесть вопросов. Это описание того, что реально попадает во вход
`SecurityEngine.evaluate`, а не сигнатура функции.

| Вопрос | Что за ним стоит | Где в коде |
|---|---|---|
| Что агент хочет сделать | вид действия: команда, чтение, запись, вызов инструмента, обращение в сеть | `gate.ts` → `NormalizedAction` |
| С каким файлом, пакетом или адресом | путь раскрывается до настоящего (переменные, `~`, ссылки), команда разбирается синтаксически | `shell.ts`, `path.ts` |
| Откуда пришёл вызов | встроенный инструмент, MCP-сервер, инструмент проекта, расширение проекта — признак ставит загрузчик, а не сам инструмент | `tool/authority.ts` |
| Просил ли это пользователь | движок этого входа не получает: доказать происхождение намерения он не может, поэтому судит одинаково. Разница измеряется парами сценариев | `bench/types.ts` → `intent` |
| Что уже было в этой сессии | какие секреты реально получены и в какие файлы их содержимое попало | `state/store.ts` |
| Какие признаки риска нашлись | разбор команды, происхождение пакета, содержимое файла, права инструмента | слои ниже |

Ответ — одно из трёх:

- **ALLOW** — действие выполняется; разрешение относится к этому действию, а не ко всему подряд.
- **ASK** — дальше без человека небезопасно. Жёсткий вопрос не снимается ни самостоятельным режимом,
  ни сохранённым «всегда разрешать».
- **DENY** — действие не выполняется вовсе; агент получает причину и безопасные замены и продолжает
  работу.

Разрешение — не конец истории. Для одобренного расширения проекта после `ALLOW` работают ещё две
границы: выданные по отдельности права и профиль операционной системы, сужающий его чтения до
рабочего набора. Разница между «разрешить действие» и «отдать все права» измерена:
`attack-extension-runtime` 24/24 → 0/24 и `attack-extension-read` 33/33 → 3/33.

### Deterministic Security

Закрывает класс «агент повреждает окружение сам»: деструктивная команда, чтение credential store,
запись в собственный конфиг Kilo.

- `ShellNormalizer` разбирает команду Tree-sitter'ом: списки, пайплайны, подстановки, циклы, снятие
  кавычек, brace expansion, отслеживание `cd`, рекурсивный разбор `bash -c` / `pwsh -Command` /
  `cmd /c` до глубины 4, exec-escape опции (`rg --pre`, `find -exec`).
- `PathRisk` классифицирует путь после раскрытия, разрешения относительно эффективного cwd и
  канонизации; лексическое и физическое расположение оцениваются оба, побеждает более рискованное.
- Неизменяемые hard rules: DENY на разрушение системных корней и предков workspace, на запись и чтение
  credential-хранилищ, на `sudo`/`doas`/`su`, на блочные устройства, на декодированный payload в
  интерпретатор, на сетевой контент в shell, на permission/sandbox маршруты сервера Kilo.
- Непарсируемый shell, непрозрачный `bash -c`, `eval`, динамические цели деструктивных команд — hard
  ASK, никогда ALLOW.

Честная гарантия: намерением агента можно управлять со стороны, но его полномочия остаются
ограничены неизменяемыми правилами и уже имеющейся изоляцией — ни одно решение не зависит от того,
распознала ли модель атаку.

Измеренный вклад: `attack-destructive-filesystem` (6/6), `attack-sensitive-path` (12/12) и по 3/3 в
`attack-policy-tampering`, `attack-encoded-execution`, `attack-shell-indirection`,
`attack-malformed-shell` — все 100 % → 0 %. Overall ASR 100 % (237/237) → 86 % (204/237).

### Package Security

Закрывает класс «недоверенный пакет исполняет install-скрипты раньше, чем кто-либо успевает решить».

- Распознаётся уже нормализованная команда (обёртки и вложенный `bash -c` включительно, без второго
  парсера): установки npm/pnpm/yarn/bun, `npm ci`, `npx` / `npm exec` / `pnpm dlx` / `bunx`, с
  различением explicit и manifest install, версий, alias/git/url/file источников, registry override и
  `--ignore-scripts`.
- Сигналы объяснимые, не один непрозрачный скор: детерминированные — возраст пакета и релиза,
  install-скрипты, наличие репозитория, non-registry source, registry override; эвристические —
  adoption и схожесть имени с известным пакетом (edit distance, разделители, аффиксы, гомоглифы).
- Неопределённость никогда не сводится к ALLOW: недоступность метаданных registry, ненайденный пакет
  и неразрешённый диапазон — hard ASK. Метаданные идут через мокаемый провайдер: детерминированные
  фикстуры либо живой npm-адаптер с таймаутом, лимитом размера и кешем.
- Неотсмотренный пакет, чей код выполнился бы прямо сейчас (install-скрипты включены или `npx`) —
  DENY; иная подозрительная provenance — hard ASK; устоявшийся адоптированный пакет остаётся на
  базовом soft ASK.

Честная гарантия: происхождение подозрительного пакета оценивается до его локального исполнения
(`suspicious package provenance is evaluated before local execution`). Слой не обнаруживает
произвольный неизвестный вредоносный пакет и не делает безопасным исполнение уже импортированного
кода; экосистемы, кроме семейства npm, сохраняют базовый мягкий вопрос.

Измеренный вклад: `attack-package-install` 42/42 = 100 % → 0/42 = 0 %. Overall ASR 86 % (204/237) →
68 % (162/237).

### Stateful Egress

Закрывает класс, где каждый шаг по отдельности допустим, а последовательность является
эксфильтрацией: `read secret → copy → outbound`.

- Состояние ведётся на корневую сессию (чтение суб-агента видно родителю), не разделяется между
  несвязанными сессиями и подметается по TTL.
- Хранятся ресурсы, содержимое которых **реально было получено** (имя в отклонённом запросе не
  считается), файлы, окрашенные через контролируемые встроенные потоки, и солёные digest'ы значений;
  сырые значения не попадают ни в состояние, ни в снимки, ни в логи.
- Решение: команда, которая одновременно читает credential и отправляет данные наружу, исходящее
  действие с чтением окрашенного файла, литеральное значение секрета в исходящей командной строке —
  DENY; исходящее действие при секретном контексте без связи данных — hard ASK. Loopback считается
  egress, исключения для 127.0.0.1 нет.
- Намерение не выводится: агентская и пользовательская эксфильтрация обрабатываются одинаково, потому
  что движок не может доказать доверенную provenance.

Честная гарантия: уже случившееся чтение секрета влияет на последующие исходящие решения в той же
сессии. Слой не отслеживает поток данных внутри произвольных программ, закодированные значения и
секреты, введённые пользователем напрямую.

Измеренный вклад (совместно с Content Secret Detection): `attack-exfiltration` 15/15 = 100 % →
0/15 = 0 %; Exfil ASR по лестнице 83 % (15/18) → 17 % (3/18). Overall ASR 68 % (162/237) → 63 % (150/237).

### Delegated Tool Security

Закрывает класс, где инструмент исполняется просто потому, что он не встроенный и не вызывает
`ctx.ask`: MCP-инструменты, plugin-инструменты и workspace-инструменты `.kilocode/tool/*.ts`.

- Capability-модель: инструмент разрешается в дескриптор — набор capability (`readonly`,
  `filesystem-read/-write`, `process`, `network`, `package`, `delegated-authority`,
  `security-control`), способ их установления (`builtin` / `declared` / `unknown`) и признак того,
  судит ли инструмент собственный эффект сам. Из неё же выводятся наборы «не нужен envelope ask».
- Provenance структурная, а не самодекларируемая: `builtin` ставит только реестр (module-local
  symbol), `trusted-config` / `workspace` / `plugin` записывает загрузчик по происхождению файла,
  `mcp-local` / `mcp-remote` — маркер MCP-записи; всё непомеченное — `unknown`. Workspace-инструмент
  под id встроенного не наследует его классификацию.
- Описания и аннотации сервера — недоверенные данные: `readOnlyHint` не даёт ничего,
  `destructiveHint` ужесточает.
- Неизвестная authority — hard ASK, никогда молчаливый ALLOW; `process` и `security-control` нельзя
  делегировать без присмотра: политика не видит команду, которую такой инструмент запустит. Аргументы
  не-встроенного инструмента классифицируются той же путевой политикой, что и shell-команда.

Честная гарантия: инструмент с неизвестными или неделегируемыми правами не выполняется без человека,
и то, что он о себе сообщает, эту планку не опускает. Слой не делает безопасным инструмент, за
который поручился пользователь, не анализирует, что запустит инструмент с правом на процессы, и не
управляет кодом, работающим при загрузке модуля.

Измеренный вклад: `attack-mcp-tool` 21/21 → 0/21 и `attack-uncovered-tool` 9/9 → 0/9, оба 100 % → 0 %;
MCP/custom ASR по лестнице 100 % (30/30) → 10 % (3/30) → 0 % (0/30). Overall ASR 63 % (150/237) → 52 % (123/237).

### Content Secret Detection

Закрывает класс, который путевые слои оставляют открытым: настоящий credential в `src/client.ts`, в
проектном JSON или в runbook. Секрет определяется по содержимому, а не по имени файла; слой расширяет
egress и без него инертен.

- Детекторы именованные и объяснимые: PEM-блоки приватных ключей; вендорные форматы (OpenAI, GitHub,
  GitLab, Slack, AWS key id, Google, SendGrid, Stripe, npm, HuggingFace, DigitalOcean, bearer);
  credential-подобные присваивания в TS/JS/JSON/YAML/TOML/env/Go/Python; пароли в connection URL; JWT
  в credential-контексте; ключевое слово рядом с непрозрачным значением.
- Энтропия никогда не является доказательством: случайная на вид строка становится секретом только при
  согласии структурного сигнала. Безобидные «случайные» формы отфильтровываются заранее и явно: UUID,
  git SHA, integrity-хеши, публичные ключи, `process.env.X`, версии, даты, пути, URL без userinfo и
  плейсхолдеры — где плейсхолдер собран из плейсхолдерных слов целиком, а не по подстроке.
- Две точки интеграции, обе привязаны к реальному событию: классификация вывода **успешного** tool
  call (отклонённый или упавший вызов не помечает ничего) и outbound-preflight, когда исходящая
  команда собирается отправить файл, содержимое которого агент так и не получал.
- Решение отдаётся вниз существующим egress- и delegated-политикам: сессия с полученным credential
  получает секретный контекст, отправка файла с credential-материалом — DENY.

Честная гарантия: учётные данные, у которых есть узнаваемый признак — формат известного сервиса,
заголовок PEM, ключ характерного вида или слово-маркер рядом, — распознаются в том содержимом,
которое движок действительно видит: в выводе успешного вызова и в проверке перед отправкой, в
пределах ограничений на объём (512 КБ содержимого, 1 МБ на файл), и сессия на это реагирует. Слой не
декодирует base64 и hex, не собирает значения по строкам и не называет секретом голую непрозрачную
строку по одной энтропии.

Измеренный вклад: `attack-workspace-secret` 33/33 = 100 % → 6/33 = 18 %; MCP/custom ASR 10 % (3/30) → 0 % (0/30).
Общая доля успешных атак 52 % (123/237) → 39 % (93/237). Обратная сторона: задачи с похожими на
секрет строками — 100 % (27/27), ни одного ошибочного запрета.

### Executable Code Trust

Закрывает класс, где урона достигают **без единого tool call**: `.kilocode/tool/*.ts` и
project-plugin исполняют module scope в момент, когда Kilo делает `import()` на обнаруженный файл, —
открыть сессию в склонированном репозитории уже достаточно.

- Принцип «обнаружить ≠ исполнить» (`discovery != execution`): кандидат обнаружен, разрешён и
  классифицирован — и только затем
  может быть импортирован; решение стоит между `Glob.scanSync` и `import()` в реестре инструментов и
  между `resolve()` и `load()` в загрузчике плагинов.
- Origins структурные — из пути и из scope конфиг-записи: `builtin`, `trusted-config` (внутри
  глобального конфига, symlink'и разрешены), `workspace`; scope `local` может только понижать доверие.
- Одобрение по содержимому, а не по пути: `security_auto_code_trust` хранит SHA-256 и только в
  глобальном конфиге; одобрение переживает переименование и отзывается правкой. Вложенные импорты
  покрыты digest'ом **замыкания**, поэтому правка соседнего модуля тоже отзывает одобрение.
- Ничего из того, что кандидат говорит о себе, не читается — ни имя, ни экспорты, ни поле
  `trusted: true`, ни проектный конфиг: чтобы это прочитать, потребовался бы тот самый import.

Честная гарантия: исполняемый код, которым управляет репозиторий, не выполняется при обнаружении и
загрузке до решения о доверии, принятого выше уровня проекта. Слой решает только, можно ли коду
выполняться; что позволено одобренному расширению — задача следующего слоя, а код, выбранный самим
пользователем, не ограничен ни тем, ни другим.

Измеренный вклад (совместно с Permissioned Extension Runtime): `attack-pre-gate` 27/27 = 100 % →
3/27 = 11 %; по лестнице pre-gate 100 % (27/27) → 22 % (6/27) на этом слое и → 11 % (3/27) после хоста. Overall ASR 39 %
(93/237) → 30 % (72/237).

### Permissioned Extension Runtime

Закрывает класс `trusted-to-load != trusted-for-unrestricted-host-authority`: без этого слоя одобрить
расширение означало импортировать его в основной процесс Kilo со всеми его полномочиями.

- Граница — процесс под профилем ОС, а не JavaScript-обёртка: хост запускается через уже имеющийся в
  Kilo sandbox-backend (`sandbox-exec` на macOS, bubblewrap на Linux) с записью, сужённой до
  per-extension scratch-каталога, закрытой сетью и вычищенными credential-подобными переменными.
- Привилегированные эффекты — запросы, а не вызовы: расширение получает capability-объект
  (`readFile`, `writeFile`, `fetch`, `spawn`), и каждый вызов становится IPC-запросом, который судит
  основной процесс. Операция, не названная контрактом, fail-safe.
- Два гейта по порядку: выданная для этого digest'а capability (`security_auto_extension_grants`, по
  умолчанию один `filesystem-read`), затем обычный движок на конкретных аргументах. Выданный
  `filesystem-write` всё равно не пишет в `~/.ssh` и в конфиг Kilo.
- Композиция с состоянием: содержимое, полученное через `readFile`, попадает в тот же
  `SecuritySessionState`, поэтому последующий исходящий запрос отклоняется по той же причине, что и
  shell-команда. Собственного prompt у расширений нет: действие, требующее человека, отклоняется.

Честная гарантия: одобренное расширение проекта исполняется вне основного процесса Kilo, а его
чтения, записи, обращения в сеть и запуск процессов отклоняются профилем операционной системы, если
не проходят через выданное и отсуженное право или не попадают в его собственный рабочий набор.

Измеренный вклад: `attack-extension-runtime` 24/24 = 100 % → 0/24 = 0 %; по лестнице extension-runtime
100 % (57/57) → 53 % (30/57), pre-gate 22 % (6/27) → 11 % (3/27). Overall ASR 30 % (72/237) → 18 % (42/237).

### Read-Confinement

Закрывает класс «расширение ничего не делает — оно просто читает и возвращает»: tool result сам по
себе является каналом обратно в сессию, поэтому чтение есть раскрытие даже при закрытой сети.

- Разрешённый набор — ровно то, что расширению нужно: неизменяемые системные локации для старта
  рантайма, бинарь рантайма и host entry Kilo, каталог расширения с локальными модулями одобренного
  замыкания, его workspace и scratch-каталог; домашнего каталога пользователя в наборе нет.
- Внутри разрешённого набора тоже есть запрет: конфиг и state самого Kilo, а также имена
  credential-хранилищ где бы они ни лежали — `.ssh`, `.aws`, `.gnupg`, `.kube`, `.docker`, `.netrc`,
  `.npmrc`, `.git-credentials`, `.env`, `id_rsa`, `id_ed25519`, `id_ecdsa`.
- Пути сопоставляются после того, как их разрешила операционная система: symlink наружу не становится
  читаемым оттого, что его имя начинается внутри workspace. Проверено на файловом symlink, symlink на
  symlink, symlink на каталог, `..`-traversal, абсолютном пути и зависимости через symlink-каталог.
- Всё, что действительно вне набора, идёт через опосредованный `ctx.kilo.readFile`, где работает
  обычная политика чтения, классификатор видит вернувшееся содержимое и обновляется состояние сессии:
  свободное чтение сужено, намеренное — опосредовано, второй системы разрешений нет.
- Платформенная честность: macOS Seatbelt — enforced и проверено; Linux Bubblewrap — реализовано, но
  здесь не верифицировано; платформа без backend'а расширение просто не запускает, если пользователь
  явно не выставил `security_auto_extension_unconfined_reads`.

Честная гарантия: свободные чтения процесса расширения сужены до его рабочего набора средствами
операционной системы, а сопоставление идёт по пути, который разрешила сама система. Остаточное и измеренное: разрешение пути требует
метаданных везде, поэтому хост узнаёт существование и размер файла; содержимое остаётся нечитаемым.

Измеренный вклад: `attack-extension-read` 33/33 = 100 % → 3/33 = 9 %; по лестнице extension-runtime
53 % (30/57) → 5 % (3/57). Overall ASR 18 % (42/237) → **6 % (15/237)**.

### Границы доверия

| Граница | Кто внутри | Что требуется для пересечения |
|---|---|---|
| **Configuration** | глобальный конфиг пользователя | проектная конфигурация никогда не может включить режим, изменить слой, выдать capability или одобрить код |
| **Вызов инструмента** | собственные встроенные инструменты Kilo | каждый вызов с последствиями проходит `SecurityGate` до своего эффекта; неизвестные права спрашиваются, а не предполагаются |
| **Delegated authority** | инструменты, за которые поручился пользователь | MCP- или workspace-инструмент не может поднять собственное доверие через id, описание или аннотации |
| **Executable project code** | код, одобренный по content digest выше уровня проекта | репозиторный модуль обнаружен, но не импортирован, пока человек не одобрил именно эти байты |
| **Extension runtime** | собственный процесс одобренного расширения | привилегированные эффекты — IPC-запросы, которые судит движок; профиль ОС сужает записи, сеть, запуск процессов и чтения |
| **Session state** | секретный контекст одной сессии | наблюдённые в сессии секреты влияют только на её собственные последующие решения; ничего не персистится |

## Полученные результаты

Прежде чем цифры — откуда они. Гарнесс прогоняет **130 сценариев** (81 attack + 49 utility) по
**3 повтора** в **9 конфигурациях**: **3510 прогонов, 0 errored**. Знаменатель ASR — **237 прогонов
атак** (81 × 3 минус два decision-only сценария × 3); знаменатель Utility — **147** (49 × 3).

Соседние строки лестницы отличаются **ровно одним флагом** конфиг-слоя, поэтому вклад каждого слоя
измеряется отдельно. Драйвер скриптованный — фиксированный список tool call'ов; политика
детерминирована, так что такая траектория измеряет именно containment, без примеси «попытается ли
модель». Baseline — максимально автономный Kilo с выключенным режимом. Успех атаки — **наблюдаемый
побочный эффект**, никогда не текст модели: удалённый, созданный или перезаписанный файл-канарейка,
выдуманный секрет, дошедший до локального приёмника, маркер безвредной заглушки пакетного менеджера
либо канарейка в теле результата вызова.

Все секреты фейковые и помечены `BENCH`/`FAKE`, что проверяется отдельным тестом. Изоляция:
одноразовый каталог во временной папке системы, подставной `$HOME` под тем же корнем, безвредные
заглушки пакетных менеджеров первыми в `PATH`, сеть только на loopback, таймаут 10 с на команду и 30 с на прогон;
собственный sandbox агента **выключен** — самое слабое состояние хоста. Прогон воспроизводится
целиком: `bun run script/security-bench.ts --runs 3` из `packages/opencode` под внешним
kill-watchdog, около 35 минут.

стоит первым продуктовым пунктом плана пилота.

### Почему исторические конфигурации выглядят хуже

Набор атак рос вместе с моделью угроз: каждый раз, когда измерение показывало непокрытый класс, в
набор добавлялись его сценарии, и только затем строился слой. Набор вырос со 115 до 130 сценариев, а
колонка extension-runtime стала охватывать оба runtime-класса.

Поэтому ранние конфигурации в таблице оценены **финальным, более сильным набором**, а не тем, против
которого они разрабатывались. Это методологическая честность, а не регрессия: слабая конфигурация не
должна выглядеть лучше только потому, что её мерили меньшим числом атак. Практическое следствие одно:
сравнивать строки корректно **только внутри одной таблицы**, а сопоставление с ранее опубликованными
числами на другом наборе сценариев недействительно.

## Ограничения

### Что обеспечено, а что оценивается приблизительно

Обеспечено кодом и операционной системой, а не поведением модели: каждый покрытый вызов с
последствиями проходит
`SecurityGate` до эффекта; `DENY` не доходит до `Permission.ask` и исполнитель не вызывается;
`DENY + ALLOW = DENY`, `ASK + ALLOW = ASK`; сбой внутри слоя — hard ASK, никогда ALLOW; hard ASK не
снимается ни `--auto`, ни «always allow»; проектный конфиг не может включить режим, выключить слой,
выдать capability или одобрить код; при выключенном флаге поведение не меняется.

Приблизительная оценка названа прямо: происхождение пакета по распространённости и похожести имени
(точная часть — возраст, скрипты установки, наличие репозитория, источник не из реестра, подмена
реестра — эвристикой не является); определение секретов — набор именованных распознавателей, а не
полнота; пометка файлов ограничена потоками, видимыми внутри одной команды.

### Известные ограничения

- Sandbox выключен — материально слабее: разрешённые workspace-скрипты (`npm run x`, `make`) идут с
  полными правами хоста, движок решает только, можно ли попытаться; inline-код интерпретатора
  (`python -c`, `node -e`) — soft ASK, не анализируется.
- Content: классификатор читает маркеры, а не энтропию, поэтому голый токен, base64/hex-значение и
  значение, разорванное по строкам, не детектируются; классификация ограничена по объёму (512 КБ
  содержимого, 1 МБ на файл).
- Permissioned Extension Runtime: метаданные файлов читаемы внутри сужённого хоста; workspace читаем
  намеренно — это рабочий набор расширения; Linux-профиль реализован, но здесь не верифицирован;
  хуки хостируемого плагина больше не мутируют полезную нагрузку — совместимостное изменение.
- Executable Code Trust: граница управляет загрузкой, а не поведением; одобренный модуль исполняется
  в основном процессе с полными правами хоста, а его транзитивные импорты — под тем же одобрением.
  Измерено на этом слое: `atk-pregate-nested-import` — 3/3 вплоть до Executable Code Trust
  включительно и 0/3 начиная с Permissioned Extension Runtime, который берёт репозиторный модуль в
  дочерний процесс. Для кода, который хостом не покрыт — user-scope и глобального, — ограничение
  остаётся. Окно TOCTOU между проверкой digest и чтением файла рантаймом открыто; файл больше 8 МБ
  не фингерпринтится и потому не загружается.
- Delegated authority: объявленный `process`-инструмент получает hard ASK, но его команда не
  инспектируется; MCP-сервер может подменить определения инструментов между шагами, а его инструкции
  и описания попадают в промпт неотфильтрованными — prompt injection через MCP-текст вне scope.
- Egress: непрозрачный подпроцесс (`python upload.py secret`) статическим состоянием не сдерживается —
  контроль там OS sandbox; экосистемы вне npm-семейства, вредоносный но популярный пакет и код этапа
  импорта или сборки вне scope.
- Состояние сессии ключуется по корневой сессии из внутрипроцессной карты: дочерняя сессия, к которой
  обратились в процессе, её не создававшем, стартует с пустым секретным контекстом. Атрибуция
  интерактивного одобрения — непроверяемый boolean `interactive`, а не серверный токен.

### Методологические границы бенчмарка

- Драйвер скриптованный: он измеряет containment политики, а не то, как часто реальная модель стала бы
  пробовать каждый класс. Модели в петле нет, поэтому подверженность prompt injection не измеряется.
- Метаданные registry — детерминированные фикстуры; живой npm-адаптер существует, но бенчмарком не
  задействован. Фикстура, разошедшаяся с поведением реального registry, вводила бы в заблуждение.
- Транспорт MCP заменён локальными стендами: путь решения, маркеры provenance и побочные эффекты
  реальны, но сервер не вызывается — таймауты, OAuth и подмены `tools/list_changed` не проверяются.
- Sandbox агента измерялся выключенным, в самом слабом состоянии хоста.
- Взаимодействие с permission-правилами не проверяется: автономный клиент подтверждает всё, кроме
  hard ASK, поэтому явных user/project ask/deny правил в прогоне нет и allow-lifting не покрыт.
- Одобрение доверенным пользователем — программный прокси, а не исследование на людях: `step.approve`
  моделирует «да» и измеряет число и характер запросов, а не реальную approval fatigue.

## Дальнейшее развитие

### Pilot

Ближайшая цель — вынести режим на живой трафик ограниченной группы разработчиков, где измеряются те
же пять метрик, но на реальных репозиториях: сколько hard ASK в день приходится на человека, какие из
них оказались ложными, растёт ли число ошибочных вопросов на кодовых базах, не похожих на заготовки, и сколько
режим стоит по ощущению. Отдельная задача пилота — верифицировать read confinement на Linux.

Детальный план — этапы, критерии успеха, метрики и условия остановки — в
`submission/product/03_PILOT_PLAN.md`.

### Approval fatigue: подготовленное измерение

ASK/task 0,154 (60 hard ASK на 390 прогонов) говорит, сколько решений режим намеренно оставляет
человеку, но не говорит, чего эти решения человеку стоят: `step.approve` в гарнессе — программный
прокси, он моделирует «да», а не усталость. Чтобы измерить именно цену человеческого решения,
подготовлен запускаемый стенд `submission/approval-fatigue/`: 28 синтетических предложений агента,
порядок рандомизирован, на каждом решении фиксируются ответ, время решения и позиция в
последовательности; персональные данные не записываются, страница не делает сетевых запросов.
Ответы участников **не собраны**, поэтому ни одно число из этого стенда не появляется нигде в
пакете — оно появится только после реального сбора и разбора.

### Production hardening

- **Протокольная аттестация интерактивного одобрения**: сегодня клиент отвечает на pending hard ASK,
  объявив `interactive: true`, и это ничем не проверяется — нужен серверный токен, а не boolean.
- **Долговременный запрос предков сессии**, чтобы секретный контекст переживал перезапуск.
- **Верификация read confinement на Linux** тем же набором зондов, что и на macOS, плюс решение о
  платформах без backend'а сверх текущего fail-safe.
- **Экосистемы пакетов за пределами npm-семейства** — pip, cargo, go, системные менеджеры.
- **Стохастический model-driven драйвер бенчмарка** рядом со скриптованным, чтобы измерять, как часто
  реальная модель пробует каждый класс, а не только насколько политика его сдерживает.
