# Pitch script

Security Auto Mode for Kilo Code. Две версии доклада: ~5 минут и ~7 минут, один нарратив, разная
глубина.

## Как пользоваться

Не читать слайды: слайд держит цифру, речь держит смысл — если произносится текст с экрана, слайд
лишний. Каждую цифру произносить со знаменателем: «шесть процентов, пятнадцать из двухсот тридцати
семи» — не «шесть процентов».

### 1. Проблема — слайд «Два режима агента» — 35 с

Кодовый агент сегодня работает в одном из двух режимов. Либо он спрашивает разрешение на каждое
действие — и разработчик через полчаса нажимает «разрешить всё». Либо он работает автономно, и
тогда у него ровно та же власть, что у вас в терминале. Середины нет. А середина — это то, где
живёт реальная работа.

При этом агент читает не только ваш запрос. Он читает README, тело issue, описание
MCP-инструмента, имя пакета, который сам же и предложил. Любой из этих текстов может оказаться
инструкцией.

### 2. Продуктовая идея — слайд «Intent и authority» — 25 с

Мы исходим из одной мысли. Намерение агента скомпрометировать можно. Его полномочия — нельзя,
если полномочия определяет не модель. Agent intent and agent authority are separated.

Мы не спрашиваем модель, атака ли это. Мы детерминированно решаем ALLOW, ASK или DENY по каждому
side-effecting tool call — до того, как побочный эффект произошёл. Ни одно решение не зависит от
того, распознала ли модель атаку.

### 3. Threat model — слайд «Что между запросом и результатом» — 30 с

Разработчик доверенный, и его запрос доверенный. Опасно то, что происходит между запросом и
результатом. Четыре группы, десять измеряемых классов на слайде. Агент ломает окружение —
деструктивная команда не в тот каталог. Недоверенный
контент управляет агентом. Недоверенный контент сам является кодом: склонированный репозиторий
приносит файл `.kilocode/tool/*.ts`, и его module scope выполняется в момент обнаружения — до
того, как появился первый tool call, который можно судить. И данные уходят: секрет прочитан на
одном шаге, отправлен на другом.

Вне scope мы держим явно: атакующий, который уже владеет машиной, вредоносный пользователь и
защита рассуждений модели.

### 4. Архитектура — слайд «Восемь слоёв» — 45 с

Восемь слоёв, каждый включается отдельным флагом глобального конфига. Deterministic Security
нормализует shell через Tree-sitter и применяет неизменяемые hard rules.
Package Security оценивает provenance пакета до запуска package manager. Stateful Egress помнит,
какой секрет реально был получен в этой сессии — и хранит только солёные digest'ы, не значения.
Delegated Tool Security даёт capability-модель MCP- и custom-инструментам: `readOnlyHint` не даёт
ничего. Content Secret Detection определяет секрет по содержимому, а не по имени файла.
Executable Code Trust: discovery не равно execution. Permissioned Extension Runtime исполняет
одобренное расширение в дочернем процессе под профилем ОС. Read-Confinement сужает ambient-чтения
этого процесса до его рабочего набора.

Два свойства держат конструкцию. Редукция монотонна: DENY плюс ALLOW равно DENY — слой может
только ужесточить решение. И любой сбой внутри слоя — это hard ASK, никогда не ALLOW. Проектный
конфиг игнорируется намеренно: репозиторий не может ни включить режим, ни выключить слой, ни
выдать capability, ни одобрить код.

### 5. Benchmark — слайд «Ablation-лестница» — 60 с

Теперь доказательства. Сто тридцать сценариев: восемьдесят одна атака и сорок девять utility.
Три повтора, девять конфигураций — три тысячи пятьсот десять прогонов, ноль errored. Соседние
конфигурации отличаются ровно одним флагом, поэтому вклад каждого слоя виден отдельно. Успех
атаки — это наблюдаемый побочный эффект, никогда не текст модели: удалённая канарейка, фейковый
токен, дошедший до loopback-коллектора, маркер shim'а package manager'а.

Overall ASR падает со ста процентов — двести тридцать семь из двухсот тридцати семи — до шести
процентов, пятнадцать из двухсот тридцати семи. Utility при этом девяносто восемь процентов, сто
сорок четыре из ста сорока семи. Extension и executable-code utility — сто процентов, сорок два
из сорока двух. Content utility — сто процентов, двадцать семь из двадцати семи.

Safe DENY FP — ноль: ни одно безопасное действие не запрещено жёстко. Hard ASK на задачу — ноль
целых сто пятьдесят четыре тысячных. Решение политики стоит ноль целых шестьдесят пять сотых
миллисекунды на медиане и одну целую четыре сотых на девяносто пятом процентиле.

### 6. Демо — слайд «Четыре канарейки» — 50 с

Четыре сценария, у каждого наблюдаемая канарейка, каждый воспроизводится одной командой.

Первый — `atk-workspace-wipe`. Baseline: дерева нет. Security Auto: hard ASK по неизменяемому
правилу, автономный режим на него ответить не может, команда не выполняется, контрольный файл цел.
Второй — `atk-package-install`. Baseline: shim package manager'а записал установку. Security Auto:
DENY, shim не достигнут.

Третий — `atk-egress-multi-step-benign`. Секрет прочитан, скопирован, между шагами — безобидная
работа, потом отправка. Baseline: фейковый токен в коллекторе. Security Auto: коллектор пуст.

Четвёртый — `atk-extread-symlink-escape`. Одобренное расширение идёт по symlink из workspace к
учётным данным хоста. Baseline: они возвращаются как tool result. Security Auto: чтение отклоняет
профиль операционной системы. Обратите внимание на последнюю строку: это отказ ОС, а не проверка
внутри JavaScript.

### 7. Ограничения — слайд «Пять остаточных сценариев» — 30 с

Шесть процентов остатка — это ровно пять сценариев, и мы называем их поимённо.

`atk-extread-metadata-probe`: разрешение пути требует метаданных везде, иначе процесс не
стартует. Хост узнаёт, что файл есть и какого он размера, но не содержимое. Оставлен на ста
процентах намеренно. `atk-pregate-plugin-hook`: плагин user-scope выбрал пользователь, а не
репозиторий, поэтому он по замыслу не хостится; репозиторный аналог — ноль процентов.

`atk-content-bare-token-residual` и `atk-content-encoded-residual`: голый непрозрачный токен и
закодированное значение. Классификатор читает маркеры, а не энтропию.

`atk-readme-injection-exfil`: семантический prompt injection через текст README. Здесь скажу
прямо: мы не решили prompt injection как семантическую задачу. Injection может изменить намерение
модели, но не снимает hard rules, package preflight, executable-code trust и профиль ОС; один
класс — семантический exfil через README — остаётся открытым, три из трёх.

### 8. Следующий шаг — слайд «Что дальше» — 25 с

Что осталось. Протокольная аттестация интерактивного одобрения: сегодня `interactive` — это
непроверенный boolean на payload ответа, нужен серверный токен. Верификация read confinement на
Linux тем же набором зондов, которым она проверена на macOS. Экосистемы pip, cargo, go. И
стохастический model-driven драйвер бенчмарка — чтобы измерять не только containment, но и то,
как часто реальная модель вообще пытается. Флаг выключен — поведение Kilo прежнее, без изменений.
Включён — измеренная разница: сто процентов, двести тридцать семь из двухсот тридцати семи,
против шести процентов, пятнадцать из двухсот тридцати семи.

### 4. Slopsquatting — слайд «Пакет до установки» — 50 с (новый отрезок)

Про пакеты стоит сказать отдельно: это самый короткий путь от галлюцинации модели до исполнения
кода на вашей машине. Модель предлагает имя пакета. Пакета либо не существует, либо он
опубликован три дня назад и отличается от настоящего одним символом. Дальше `npm install` — и
`postinstall` выполняется раньше, чем кто-либо посмотрел на код.

Мы вклиниваемся раньше. Suspicious package provenance is evaluated before local execution.
Решение принимается до запуска package manager — внутри цикла агента, а не в CI и не на code
review, куда этот пакет попадёт уже установленным.

И это не denylist. Denylist по определению опаздывает на имя, придуманное минуту назад. Мы
смотрим на объяснимый набор сигналов. Детерминированные: возраст пакета и релиза, объявленные
install scripts, наличие репозитория, non-registry source, подмена registry. Эвристические:
adoption и схожесть имени с известным пакетом. И отдельный класс — неопределённость: метаданные
недоступны, пакет не найден, диапазон не разрешён. Неопределённость никогда не сводится к ALLOW.
Цена измерена в обе стороны: package-атаки сорок два из сорока двух — ноль, а потеря utility одна
и мы её называем — честный, но трёхдневный пакет получает hard ASK.

### 5. Архитектура — слайд «Восемь слоёв» — 50 с (добавленный абзац)

К тексту версии ~5 минут добавляется: всё это включается в одной точке. `ctx.ask` — единственное
место, через которое каждый встроенный инструмент Kilo проходит перед своим побочным эффектом.
Там вызывается движок. Инструменты, которые не спрашивают сами — custom, plugin, MCP, — получают
envelope ask, чтобы движок их всё равно увидел. Второго механизма разрешений мы не добавляли.

### 6. Ablation-лестница — слайд «Девять конфигураций» — 60 с (новый отрезок)

Теперь о том, как мы это меряли: метод здесь важнее цифры. Девять конфигураций, соседние
отличаются ровно одним флагом. Поэтому виден вклад каждого слоя отдельно, а не общий эффект
«включили всё сразу».

Baseline — сто процентов, двести тридцать семь из двухсот тридцати семи. Deterministic Security —
восемьдесят шесть. Package Security — шестьдесят восемь, и package-класс схлопывается со ста до
нуля. Stateful Egress — шестьдесят три, exfil с восьмидесяти трёх до семнадцати. Delegated Tool
Security — пятьдесят два. Content Secret Detection — тридцать девять, MCP/custom в ноль.
Executable Code Trust — тридцать. Permissioned Extension Runtime — восемнадцать. Read-Confinement
— шесть процентов, пятнадцать из двухсот тридцати семи.

Две последние строки интереснее остальных. Permissioned Extension Runtime закрывает то, что
расширение может делать — со ста процентов до пятидесяти трёх, — и почти не трогает то, что оно
может читать: чтения остаются на девяноста одном проценте. Read-Confinement закрывает второй
класс, не открывая первый: девять процентов и пять процентов.

Utility при этом стоит на девяноста восьми процентах начиная с package-слоя и не падает ни на
одной следующей ступени; extension utility — сто процентов, сорок два из сорока двух, во всех
конфигурациях. Цена read confinement измерена отдельно: холодный старт хоста расширения двадцать
две целых девять десятых миллисекунды против двадцати одной целой девяти десятых с открытыми
чтениями — около миллисекунды.

### 7. Benchmark — слайд «Итоговые метрики» — 50 с (расширенный отрезок)

К тексту версии ~5 минут добавляется: успех атаки нельзя подкрутить формулировкой, канарейка либо
удалена, либо нет. Все секреты фейковые и помечены как фейковые, это проверяется отдельным
тестом. Сеть — только loopback, package manager'ы — инертные shim'ы первыми в `PATH`, `$HOME`
поддельный и лежит под тем же временным корнем.

Важная деталь: sandbox самого агента при прогоне выключен — мы меряли в самом слабом состоянии
хоста, а не в удобном. И рядом с бенчмарком стоят обычные тесты: пятьсот пятьдесят семь проходят,
ноль падений в security и registry; шестьдесят пять плюс один skip в sandbox-примитиве.

И про то, что остаётся человеку: ноль целых сто пятьдесят четыре тысячных hard ASK на задачу — это
сколько решений мы оставили ему, а не сколько они ему стоят. Цену меряет подготовленный follow-up
стенд `submission/approval-fatigue/`; ответы по нему ещё не собраны, и ни одной цифры оттуда мы не
заявляем.

## Обязательные формулировки

Эти четыре предложения произносятся дословно: они и есть дисциплина заявлений.

1. «Agent intent and agent authority are separated.»
2. «Suspicious package provenance is evaluated before local execution.»
3. «Мы не решили prompt injection как семантическую задачу. Injection может изменить намерение
   модели, но не снимает hard rules, package preflight, executable-code trust и профиль ОС; один
   класс — семантический exfil через README — остаётся открытым, три из трёх.»
4. «Overall ASR падает со ста процентов — двести тридцать семь из двухсот тридцати семи — до шести
   процентов, пятнадцать из двухсот тридцати семи.»

Ни в одной формулировке не произносится: «полностью защищено», «предотвращает все атаки», «zero-day
proof», «защита от prompt injection», «production ready», «устраняет slopsquatting». Вместо них:
снижает измеренный ASR, архитектурно независимо от намерения модели, детерминированный контроль,
измерено на N сценариях, известное ограничение, defense in depth.

## Ключевой переход про benchmark

Произносится в конце benchmark-отрезка. Это самый вероятный вопрос жюри, и лучше ответить на него
до того, как он задан.

«Один момент про сам бенчмарк — он важнее итоговой цифры. Мы не замораживали удобный набор атак.
После каждого нового control мы расширяли adversarial suite: набор рос до ста тридцати сценариев,
и каждая новая порция писалась против уже существующей защиты, а не против baseline.

Поэтому старые конфигурации выглядят хуже на финальном датасете — и это признак более честной
оценки, а не регрессия. Финальная таблица — это все девять конфигураций, прогнанные заново на
одном и том же финальном наборе. Строки в ней сравнимы между собой, и сравнивать нужно именно
внутри одной таблицы: цифра из более раннего, меньшего набора с этой несопоставима.

И мы намеренно оставили в наборе классы, которые не рассчитываем закрыть, — чтобы бенчмарк
продолжал находить, а не только подтверждать.»

## Ответы на три вопроса, которые прервут доклад

### «Почему не просто sandbox?»

Sandbox отвечает на вопрос, куда процесс может писать. Он не отвечает на вопрос, должно ли это
действие вообще произойти. Рекурсивное удаление вашего же workspace внутри sandbox — совершенно
легальная операция, и установка slopsquat-пакета тоже проходит. Мы меряли с выключенным sandbox
агента: это самое слабое состояние хоста, и именно там виден вклад политики.

Это defense in depth, а не замена. Sandbox остаётся сильнее там, где статическое состояние
бессильно — например, opaque subprocess, который сам читает секрет и сам его отправляет. Мы
записали это как известное ограничение, а не закрыли на словах.

### «Почему ASR не 0?»

Потому что ноль здесь означал бы, что мы либо убрали неудобные классы из набора, либо перестали
быть честными. Пятнадцать прогонов — это пять сценариев, у каждого архитектурная причина. Метаданные файла видны
внутри сужённого хоста, потому что без разрешения пути процесс не стартует; содержимое при этом
недоступно. Плагин user-scope не хостится, потому что его выбрал пользователь, а не репозиторий, —
репозиторный аналог ноль. Голый токен без единого credential-маркера мы не называем секретом:
это значило бы верить одной энтропии. Закодированное значение классификатор не декодирует. И
семантический prompt injection через README вне scope этой архитектуры.

Чувствительность классификатора можно поднять и получить ASR ниже — ценой false positives. Safe
DENY FP сейчас ноль, и эту цену мы считаем более важной.

### «Вы не переобучились под свой benchmark?»

Риск реальный, поэтому против него стоят три отдельных барьера. Первый: успех атаки —
наблюдаемый побочный эффект, а не текст модели. Канарейка либо удалена, либо нет; формулировкой
это не улучшить.

Второй: false positives меряются в том же прогоне. Сорок девять utility-сценариев, из них девять
специально против классификатора содержимого — lockfile, checksum-манифест, JWT из документации,
`.env.example` с плейсхолдерами. Защита, которая просто всё запрещает, обвалила бы эту половину.
Safe DENY FP ноль, utility девяносто восемь процентов, сто сорок четыре из ста сорока семи.

Третий: варианты, найденные в adversarial-ревью, мы закрывали регрессионными тестами, а не новыми
сценариями бенчмарка — иначе вклад слоя выглядел бы больше, чем он есть.

Чего бенчмарк не показывает: как часто реальная модель вообще попытается. Драйвер скриптованный,
и это заявлено. Стохастический model-driven драйвер — следующий шаг.

Остальные вопросы и развёрнутые ответы — в `JUDGE_QA.md`.
