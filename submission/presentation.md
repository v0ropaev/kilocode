## Слайд 2 — Автономия против approval fatigue

**Лид:** Полезен только автономный агент. Оба доступных режима плохие.

| Режим 1 — подтверждать каждое действие | Режим 2 — skip permissions |
|---|---|
| Человек читает десятки запросов подряд, перестаёт вчитываться и нажимает «разрешить» автоматически. Автономия, ради которой агент и нужен, исчезает. | Агент получает полную authority на машине разработчика. На максимально автономном Kilo 100 % (237/237) прогонов атак доходят до наблюдаемого эффекта. |

**Опаснее всего, когда security-решение принимает та же модель.**

| 100 % | 81 | 0 | ~1 мс |
|---|---|---|---|
| успешных прогонов атак на baseline | attack-сценарий, 49 utility | внешних вызовов в решении | p95 стоимости решения |

## Слайд 3 — Пользователь и продуктовая гипотеза

**Основной пользователь.** Разработчик, запускающий coding agent автономно. Успех — задача сделана
без цепочки подтверждений. Провал — удалённые файлы, утёкший ключ, установленный чужой пакет.

**Дополнительный пользователь.** Engineering / security lead, который решает, можно ли вообще
включить автономию в команде. Ему нужны измеримые границы, а не обещание.

> **Продуктовая гипотеза.** Если вынести authority control из LLM в детерминированный context-aware
> слой и спрашивать человека только там, где система не может решить сама, — ASR резко падает без
> существенной потери Utility.

**Мы оптимизируем безопасную автономность, а не количество блокировок.** Измеряются пять метрик
сразу: ASR, Utility, false positives, friction, latency. Конфигурация «запретить всё» даёт ASR 0 %
и решением не является.

## Слайд 4 — Threat model: intent ≠ authority

**Лид:** Доверенный разработчик. Недоверенное окружение. Модель, которой можно управлять.

| Доверено | Недоверено | Следствие |
|---|---|---|
| Разработчик и его задача. Глобальный конфиг пользователя. Собственный код Kilo. Sandbox-бэкенд операционной системы. | Рассуждение модели. Содержимое репозитория, README и docs. Имя пакета, выбранное моделью. Метаданные MCP-инструментов. Исполняемый код и конфиг проекта. | Решение не зависит от того, распознала ли модель атаку: его принимает детерминированный слой вне модели, а подтверждает профиль ОС. |

**Десять классов угроз, каждый измеряется отдельными сценариями:** деструктивные вызовы ·
чувствительные файлы · подмена политики · prompt injection · утечка секретов · многошаговые атаки ·
slopsquatting · делегированная authority MCP · код проекта · ambient authority расширения.

## Слайд 5 — Очевидные подходы и их пределы

**Лид:** Каждый решает часть задачи. Ни один не закрывает её целиком.

| 01 Prompt guardrails | 02 Denylist пакетов | 03 Только sandbox | 04 Подтверждать всё вручную |
|---|---|---|---|
| Защищают вход модели. Но если injection уже победила intent, guardrail не ограничивает то, что агент физически может сделать. | Закрывает уже известное. Свежий slopsquat по определению отсутствует в списке в момент установки. | Ограничивает эффект, но не различает легитимную работу и атаку: workspace-запись нужна и той и другой. И не работает до первого tool call. | Безопасно на бумаге. На практике даёт approval fatigue и заканчивается включением skip-permissions. |

Security Auto использует все четыре идеи, но переносит решение об authority в отдельный
детерминированный слой и подтверждает его профилем ОС там, где это выполнимо.

## Слайд 6 — Как работает Security Auto

**Лид:** Один choke point для эффектов и две границы, срабатывающие раньше tool call.

```
Agent tool call → Normalization (shell AST · пути) → Security Engine → Authority (ALLOW / ASK / DENY) → Executor / OS sandbox
                                                            ↑
                              Package Security · Stateful Egress · Delegated Tool Security · Content Secret Detection
                              evidence-слои: только ужесточают решение, никогда не ослабляют
```

**До того, как tool call вообще появится**

- **Executable Code Trust** — репозиторный `.kilocode/tool/*.ts` и project-plugin исполняют module
  scope в момент импорта. `discovery != execution`: модуль не импортируется, пока человек не одобрил
  эти байты.
- **Permissioned Extension Runtime + Read-Confinement** — одобренное расширение живёт в дочернем
  процессе под профилем ОС. Привилегированные эффекты — IPC-запросы, которые судит тот же движок.

Источник диаграммы: [diagrams/architecture.mmd](diagrams/architecture.mmd).

## Слайд 7 — Слои защиты и что каждый закрыл

**Лид:** Ниже — вклад именно этого слоя, а не накопленной суммы.

| Слой | Механизм | Вклад |
|---|---|---|
| Deterministic Security | ALLOW / ASK / DENY для каждого side-effecting вызова. Shell разбирается Tree-sitter, пути классифицируются после канонизации. | деструктивные 6/6 → 0/6 |
| Package Security | Provenance пакета оценивается до запуска package manager. Неопределённость никогда не сводится к ALLOW. | пакеты 42/42 → 0/42 |
| Stateful Egress · Content Secret Detection | Секрет, полученный на шаге N, влияет на исходящее решение на шаге M. Секрет определяется по содержимому, а не по имени. | exfil 12/15 → 0/15 · секреты 33/33 → 6/33 |
| Delegated Tool Security | Capability-модель для MCP, plugin и workspace-инструментов. Provenance структурная; `readOnlyHint` не даёт ничего. | MCP/custom 30/30 → 3/30 |

**Executable Code Trust · Permissioned Extension Runtime · Read-Confinement** — код проекта не
исполняется до решения о доверии; чтения расширения сужены профилем ОС.
**pre-gate 27/27 → 3/27 · runtime расширения 24/24 → 0/24 · чтения 33/33 → 3/33**

## Слайд 8 — Slopsquatting: решение до установки

**Лид:** Проверка внутри agent loop, а не в CI и не в pre-commit хуке.

```
Агент предлагает зависимость → Package Risk Evaluator → Provenance сигналы → Решение (DENY / ASK / ALLOW) → package manager
```

| Детерминированные сигналы | Эвристические сигналы | Неопределённость |
|---|---|---|
| Возраст пакета и релиза · объявленные install scripts · наличие репозитория · не-registry источник · подмена registry в команде или в `.npmrc` | Adoption по загрузкам · схожесть имени с известным пакетом: edit distance, разделители, аффиксы, гомоглифы, scope — с указанием, на что похоже | Метаданные недоступны, пакет не найден, диапазон не разрешён. Неопределённость никогда не сводится к ALLOW: metadata lookup failure ≠ trusted |

**Suspicious package provenance is evaluated before local execution.** Не детектор произвольного
zero-day. Пакет, чей код выполнился бы прямо сейчас, получает DENY; прочая подозрительная
provenance — hard ASK. Измерено: 42/42 → 0/42.

## Слайд 9 — Prompt injection

**Лид:** Injection может изменить намерение модели. Она не снимает hard rules, package preflight,
executable-code trust и профиль ОС.

```
Вредоносный README → Модель хочет опасное действие → SecurityEngine вне модели → Решение по действию, не по тексту
```

**Что именно не зависит от того, что «поняла» модель**

| Hard filesystem rules | Package Security · capability | Executable Code Trust · профиль ОС |
|---|---|---|
| Деструктивные операции над корнями и предками workspace, чтение приватных ключей — DENY по правилу, а не по распознаванию. | Provenance оценивается до исполнения. Инструмент с неизвестной authority не выполняется без человека. | Код проекта не импортируется до одобрения по содержимому. Чтения и сеть расширения отклоняет профиль ОС. |

Один класс остаётся открытым и назван честно: семантический exfil через текст README, `atk-readme-injection-exfil` — успешен 3/3 во всех девяти конфигурациях.

## Как пересобрать

```bash
python3 submission/build-deck.py submission/Security-Auto-ATH.pptx
soffice --headless --convert-to pdf --outdir submission submission/Security-Auto-ATH.pptx
```

Скрипт требует `python-pptx` и `Pillow`. Шаблон AI Talent Hub в репозиторий не вкладывается — это
презентация другого проекта и в ней сторонние знаки, — поэтому путь к нему задаётся явно:

```bash
ATH_TEMPLATE=/path/to/ath-template.pptx python3 submission/build-deck.py submission/Security-Auto-ATH.pptx
```

Без переменной скрипт ищет `knowbase-презентация-ATH.pptx` на два уровня выше себя и, не найдя,
завершается с сообщением, называющим ожидаемый путь. Логотипы он извлекает из самого шаблона. Перед сохранением он проверяет вёрстку:
переполнение текстовых блоков, наложения и выход за нижний край слайда измеряются по пессимистичной
подстановке шрифта (Arial / Arial Black шире, чем Inter), и сборка завершается с ненулевым кодом,
если найдена хотя бы одна проблема.
