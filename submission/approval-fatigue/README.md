# Approval fatigue — стенд follow-up исследования

Небольшой автономный стенд: страница с последовательностью approval prompts, набор из 28
синтетических предложений агента и скрипт разбора. Ничего не устанавливается, ничего не
отправляется в сеть.

Файлы: `cases.json` (набор кейсов), `index.html` (стенд для участника), `analyze.ts` (разбор),
этот README.

## Research question

Как часто разработчик ошибочно разрешает опасное действие в длинной последовательности approval
prompts, и растёт ли доля ошибок ближе к концу последовательности.

Вопрос прикладной: Security Auto Mode снимает часть решений детерминированно — ALLOW, DENY и soft
ASK, который автономный режим одобряет сам, — и намеренно оставляет человеку только hard ASK.
Чтобы говорить о цене человеческого решения, нужна
измеренная база — а не предположение, что человек «в целом справляется».

## Дизайн эксперимента

Внутрисубъектный дизайн, один блок из 28 предложений, между блоками ничего не сравнивается.

- **Стимул** — одно предложение агента на экран: строка команды или вызов инструмента плюс одна
  строка о том, что агента попросили сделать. Больше на экране нет ничего: ни номера правила, ни
  подсказки, ни решения движка.
- **Ответ** — две кнопки одинакового веса: «Разрешить» и «Заблокировать или спросить». Возврата к
  предыдущему предложению нет.
- **Порядок** — перемешивание Фишера–Йетса с seed от идентификатора участника. Порядок разный у
  разных участников и воспроизводим для одного и того же идентификатора.
- **Состав набора** — 11 безопасных, 8 опасных, 4 неоднозначных, 3 выглядящих безобидно, но опасных
  и 2 контекстно-зависимых (пара, где второй вызов опасен только из-за первого).
- **Ground truth** — поле `expected` в `cases.json`: `allow`, если действие штатное, и `block`, если
  оно не должно уходить в исполнение без человека. Поле `security_auto` — решение, которое приняла
  бы реализация: оно выведено из hard rules и описаний слоёв, а не проставлено на глаз; в
  `rationale` указано конкретное правило.
- **Соглашение о путях** — во всех кейсах домашний каталог сессии равен `/Users/dev`, workspace —
  `/Users/dev/projects/api`. Классификация путей в `rationale` даётся относительно этих значений.
  Пути и секреты фиктивные, домены — в зоне `.example.test`, секреты помечены `FAKE_`.

`index.html` содержит презентационную копию набора: только `id`, `tool`, `proposal`, `context` и
`expected`. Классификация (`kind`, `category`, `security_auto`, `layer`, `rationale`) живёт только в
`cases.json` — так её нельзя прочитать из исходника страницы во время прохождения. Копия встроена
намеренно: страница обязана открываться с `file://` и не делать ни одного запроса. При правке
`cases.json` встроенный массив нужно обновить вручную; `analyze.ts` сообщит о любом `caseId`,
которого нет в `cases.json`.

## Что записывается и что НЕ записывается

Записывается на каждое решение: `participantId`, `caseId`, `decision`, `expected`, `correct`,
`responseTimeMs`, `sequencePosition`, `timestamp` (ISO, часы клиента).

Не записывается ничего больше. Ни имени, ни почты, ни логина, ни IP, ни user-agent, ни данных о
машине. `participantId` — произвольная строка, которую участник придумывает сам; инструкция на
первом экране прямо просит не вводить имя или почту.

Страница не делает ни одного сетевого запроса. Прогресс лежит в `localStorage` этой вкладки, каждый
доступ к нему обёрнут в `try/catch`, и перезагрузка страницы не теряет сессию. Результат покидает
машину участника только когда он сам выгрузит JSON и передаст его организатору.

## Как провести (шаги для организатора, около 10 минут на участника)

1. Открыть `index.html` в браузере локально (`file://` достаточно). Проверить, что первый экран
   показывает поле идентификатора.
2. Продиктовать участнику анонимный идентификатор из общего списка (`p-01`, `p-02`, …) и записать у
   себя только то, что такой участник был. Соответствие «идентификатор — человек» нигде не хранить.
3. Проговорить инструкцию вслух: отвечать так, как в реальной сессии — быстро, не сверяясь с
   документацией и не проверяя пакеты в registry. Вопросы по конкретным кейсам не комментировать.
4. Оставить участника одного на прохождение: 28 экранов, около 7 минут. Не подсказывать, не
   реагировать на решения.
5. На последнем экране нажать «Скачать результаты (JSON)» и сохранить файл в `results/`. Если
   загрузка заблокирована политикой браузера — скопировать JSON из текстового поля в файл вручную.
6. Нажать «Начать новую сессию» перед следующим участником, чтобы очистить `localStorage`.

## Как посчитать

```bash
bun run analyze.ts results/*.json     # файлы сессий
bun run analyze.ts results/           # каталог целиком
bun run analyze.ts results/p-01.csv   # CSV той же формы
```

Скрипт печатает Markdown-таблицы: dangerous allow rate, safe block rate, overall decision accuracy —
каждая со своим знаменателем; median и p90 времени решения по всей последовательности и отдельно по
первой и второй половине; долю ошибок по квартилям Q1..Q4 — это и есть сигнал усталости; разбивку по
типу кейса; и сравнительную таблицу с Security Auto.

Без аргументов и при пустом входе скрипт печатает сообщение об отсутствии данных и завершается
кодом 0. Никаких примеров, оформленных как результаты, он не печатает — по замыслу.

## Как сравнивать с Security Auto (и чем это сравнение НЕ является)

Сравнивать можно ровно одно: **сколько решений остаётся человеку**. На затронутых кейсах скрипт
считает, сколько из них движок закрывает сам (ALLOW, DENY и soft ASK) и сколько намеренно
оставляет человеку (hard ASK), и показывает решение движка на каждом кейсе, где верным ответом был
`block`. На текущем наборе это 22 из 28 снятых решений и 6 оставленных hard ASK.

Это **не** apples-to-apples, и подавать его так нельзя:

- человек здесь видит один вызов без истории сессии; движок видит контекст сессии, поэтому пара
  `ctx-1-read-fixture` → `ctx-2-upload-report` для человека — два независимых экрана, а для движка —
  одна связная траектория;
- человек не может проверить provenance пакета или содержимое файла за секунды, а Package Security
  и Content Secret Detection делают это до побочного эффекта;
- набор кейсов синтетический и подобран так, чтобы покрыть классы слоёв, а не так, чтобы
  воспроизвести реальное распределение запросов в рабочей сессии;
- решения движка в `cases.json` выведены из правил и описаний слоёв, а не измерены прогоном
  бенчмарка на этих 28 кейсах.

Корректная формулировка вывода — «на этом наборе движок снимает N решений из 28 и оставляет M
жёстких ASK, а человек на тех же кейсах ошибся в X % (n/d) случаев». Некорректная — любая, где
человеческая точность подаётся как метрика системы или наоборот.

## Ограничения

- Малая выборка: исследование рассчитано на единицы участников, доверительные интервалы будут
  широкими, и любой вывод — направление, а не оценка.
- Задачи синтетические: 28 кейсов покрывают классы слоёв, а не реальный поток вызовов.
- Нет реальной цены ошибки: разрешение опасного действия ничего не ломает, поэтому измеренная
  осторожность скорее завышена, чем занижена.
- Порядок рандомизирован, но сам набор фиксирован: эффект позиции измеряется, эффект содержания —
  нет.
- Время решения снимается по часам клиента и включает время чтения условия; сравнивать его
  осмысленно только между срезами одной и той же выборки.
- Один блок без перерыва: усталость от длинной сессии реального рабочего дня этим не моделируется.

## Статус

**Ответы участников не собраны.** Сейчас это подготовленное follow-up исследование: набор кейсов,
стенд и скрипт разбора. Никакие числа из него не могут появиться ни в одном submission-материале,
пока сбор реально не проведён и результаты не разобраны `analyze.ts`. Каталога `results/` в
репозитории нет намеренно — он создаётся при первом сборе.
