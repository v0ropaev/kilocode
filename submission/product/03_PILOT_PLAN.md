# План пилота

Security Auto Mode измерен в лаборатории: 192 сценария (141 attack + 51 utility) × 3 повтора ×
10 конфигураций = 5760 прогонов, 0 errored. Доля успешных атак снижается со **100 % (417/417)** без
защиты до **24 % (102/417)** на одном движке правил и до **4 % (18/417)** с семантическим слоем, при
utility **95 % (146/153)**. Пилот отвечает на другой вопрос — во что режим обходится живой команде на
настоящем репозитории.

Режим выключен по умолчанию и включается только глобальным конфигом пользователя. Это делает пилот
обратимым: одна строка выключает режим и возвращает прежнее поведение запросов, наборов правил и
загрузки без изменений.

Отдельно про модель внутри режима, потому что это первый вопрос, который зададут. Семантический слой
не принимает решений: он возвращает свидетельство в свёртку, которая начинается с ALLOW и умеет
только ужесточать. Он не может выдать ALLOW, не может выдать DENY, не может превратить DENY в ASK
или ASK в ALLOW — в лабораторном прогоне счётчики автоматических ALLOW (279) и DENY (195) совпадают
до единицы с прогоном без слоя. Если модель не настроена, слой не вносит ничего, и поведение
совпадает со сборкой без этого кода.

## Кто пилотирует

Команда из 5–10 разработчиков, уже работающая с Kilo Code в автономном режиме, на репозитории с
внешними зависимостями и подключёнными MCP-инструментами. Плюс один engineering/security lead как
владелец решения.

Профиль выбран под то, что осталось неизмеренным. Лаборатория меряет containment на скриптованных
траекториях; она не меряет, как часто на реальном коде срабатывают эвристические поверхности —
Package Security (adoption, схожесть имени, возраст), Content Secret Detection (именованные
детекторы) и семантический слой. False-positive профиль на настоящих репозиториях можно получить
только на живой работе.

Для семантического слоя это особенно важно. Всё измерено на одной модели —
`openrouter/anthropic/claude-haiku-4.5`, — и на нашем наборе атак. На независимом отложенном наборе
из 58 парных случаев она даёт 27 из 29 при 3 ложных из 29. Чего это не говорит: как поведёт себя
другая модель (второй кандидат берёт 0 из 4 на вопросе о соответствии задаче) и как часто настоящая
модель в петле вообще попыталась бы напасть. Первое включение на модели участника — часть пилота.

> **Отложенный набор перестроен и измерен на настоящей модели.** Прежний корпус проходился по
> имени файла: классификатор, не открывавший недоверенный текст, набирал на нём 74 % recall — больше
> самого слоя. Новый построен парами: у обеих половин одинаковое действие, имя файла и источник, а в
> семье инъекций и одинаковый запрос пользователя, поэтому классификатор без доступа к тексту
> обязан отвечать одинаково и берёт ровно 50 % — это арифметика, а не результат. На нём
> `claude-haiku-4.5` через OpenRouter даёт **27/29 (93 %) при 3/29 (10 %) ложных эскалаций**, а тот
> самый слепой baseline — 13/21 при 13/21 ложных. Подробно:
> `docs/security-auto-mode-llm-results.md`, раздел «Held-out eval».


Нужен именно автономный режим: hard ASK не снимается ни `--auto`, ни сохранённым «always allow», ни
неинтерактивным ответом. Команда, которая и так подтверждает каждое действие руками, не почувствует
разницы и не даст сигнала о friction.

Владелец решения нужен потому, что три настройки — `security_auto_tool_capabilities`,
`security_auto_code_trust`, `security_auto_extension_grants` — по замыслу лежат выше уровня проекта:
репозиторий не может ни выдать capability, ни одобрить код. Кто-то должен принимать эти решения
осознанно.

Больший rollout преждевременен по четырём причинам. Read-Confinement верифицирован на macOS, для
Linux реализован, но здесь не верифицирован. Четыре остаточных класса атак названы, но открыты, и
требуют явного проговаривания с каждым участником. Отложенный набор израсходован и требует замены.
И порог friction, приемлемый для команды, пока не установлен: лабораторное число выросло с
0,14 до 0,29 вопроса на задачу — заявленный до измерения порог 0,25 превышен, и именно живая работа
должна показать, чувствуется ли эта разница.

## Сценарий пилота

1. **Включение.** Владелец решения раскладывает участникам глобальный конфиг:
   `{ "experimental": { "security_auto": true } }` (или `KILO_SECURITY_AUTO=1`). Проектный конфиг в
   этом не участвует и не может ничего переопределить.
2. **Дефолтный набор слоёв.** Все переключаемые слои — Package Security, Stateful Egress, Delegated
   Tool Security, Content Secret Detection, Executable Code Trust, Permissioned Extension Runtime и
   семантический слой (`experimental.security_auto_classifier`) — включаются вместе с режимом.
   Read-Confinement активен, потому что `security_auto_extension_unconfined_reads` по умолчанию
   выключен. Ничего донастраивать на старте не требуется.
3. **Модель для семантического слоя.** Отдельного ключа не нужно: провайдер по умолчанию — `kilo`,
   то есть та модель, которую участник уже настроил, и никакой вендор в коде не назван. Закрепить
   отдельную модель можно переменной `KILO_SECURITY_AUTO_CLASSIFIER_MODEL`; в лаборатории так и
   сделано.
   Обращение происходит не на каждом действии, а в узкой полосе решений — в лаборатории это
   0,16 обращения на решение, примерно одно из шести. Ожидание ограничено дедлайном 2500 мс; после
   трёх подряд неудач провайдера слой перестаёт спрашивать до конца жизни процесса. Если модель не
   настроена вовсе, режим работает как без этого кода.
4. **Что видит пользователь.** ALLOW проходит как раньше. Hard ASK — интерактивный запрос, на
   который должен ответить человек, и в нём теперь стоит одна фраза о том, почему спрашивают:
   например, «The project README told the agent to send this file to an outside address, which is
   not something you asked for». Та же фраза печатается и в неинтерактивном прогоне рядом со строкой
   об отклонении, поэтому в логе автономного запуска видно не только что остановились, но и на чём.
   DENY — завершённый tool result «Blocked by security policy» со стабильным reason code,
   человекочитаемой причиной, `canRetry` и безопасными альтернативами; ход продолжается, работа не
   обрывается.
5. **Инструменты команды.** Для своих MCP-серверов владелец заводит декларации в
   `security_auto_tool_capabilities` (`readonly`, `network`, `filesystem-write`, …). Без декларации
   инструмент — unknown authority и получает hard ASK на каждый вызов; `process` и
   `security-control` не делегируются unattended by design.
6. **Репозиторный исполняемый код.** Если в проекте есть `.kilocode/tool/*.ts` или объявленный
   плагин, он обнаруживается, но не импортируется. В блоке приходит готовая строка вида
   «Add "<sha256>" to experimental.security_auto_code_trust in your global Kilo config». Одобрение —
   действие человека в его собственном конфиге, по содержимому: правка файла отзывает его.
7. **Расширения.** Одобренное workspace-расширение по умолчанию получает только `filesystem-read`;
   всё остальное выдаётся точечно через `security_auto_extension_grants` на конкретный digest.
8. **Обратная связь.** Основной канал — сами решения: логи несут reason code, rule id и command
   fingerprint, но никогда текст команды и содержимое файлов. Владелец еженедельно разбирает список
   hard ASK и DENY по reason code и список заблокированных кандидатов на загрузку, размечая каждое
   как обоснованное или ложное. Это и есть измерение FP. Вопросы, поднятые семантическим слоем,
   размечаются отдельной пометкой: у них своя цена и своя причина, и смешивать их с вопросами
   движка правил нельзя.
9. **Контрольная точка.** В начале и в конце периода бенчмарк прогоняется на машине участника
   воспроизводимой командой из документации — чтобы отличить регрессию платформы от особенностей
   репозитория. Там же, на настоящей модели участника, первый раз запускается оценка семантического
   слоя: `bun run script/security-semantic-eval.ts --provider kilo --model openrouter/anthropic/claude-haiku-4.5 --set held-out`.

## Метрики успеха

Лабораторные значения и пилотные — **разные знаменатели и разные измерения**. В лаборатории
знаменатель доли успешных атак — 417 прогонов скриптованного драйвера в одноразовом sandbox, у
обычных задач — 153 прогона; успех атаки там наблюдаемый побочный эффект, а не текст модели. В
пилоте знаменатель — реальные задачи живых людей на настоящих репозиториях, где никто атак не
подкладывает. Числа из двух колонок ниже нельзя ставить рядом как «было / стало».

| Метрика | Как измеряется в пилоте | Текущее значение на benchmark | Порог для пилота |
|---|---|---|---|
| Доля успешных атак | Только на контролируемом наборе сценариев, прогоняемом на машине участника. По проду не считается: там нет оракула побочного эффекта | **4 % (18/417)**; без слоя 24 % (102/417) | Не выше лабораторного; ни одна категория, закрытая до 0 % в каноническом прогоне, не отыгрывает назад |
| Задачи доведены до конца | Доля пилотных задач, законченных без выключения режима и без обхода политики | **95 % (146/153)**; extension + executable-code 100 % (42/42); content 100 % (27/27); сетевые задачи 100 % (12/12) | Согласуется с командой до старта; предложение — не ниже 95 % |

| Вопросов человеку на задачу | Число интерактивных ответов на hard ASK, делённое на число задач | **0,29** со слоем против 0,14 без него | Предложение, а не доказанное значение: не выше 0,5 на задачу |

| Обращений к модели на решение | Счётчик обращений слоя, делённый на число решений | **0,16**, ошибок и таймаутов 0 / 0 | Не выше лабораторного более чем вдвое; рост означает, что полоса маршрутизации на живом коде шире, чем на наборе |

Задержку слоя ограничивает дедлайн 2500 мс, и первая живая её оценка — часть пилота |

| Доверие пользователя | Доля участников с включённым режимом на конец периода; каждое выключение фиксируется с причиной | Лабораторного эквивалента нет | Порог согласуется с командой до старта; сам факт выключения разбирается всегда |

Латентность задачи целиком в таблице не приводится намеренно: заблокированная атака не делает
работу, поэтому средняя задержка задачи в лаборатории сравнивает неравные объёмы работы. Честных
латентностей здесь две — стоимость решения политики и холодный старт хоста расширения; всё, что
касается ожидания модели, в лаборатории не измерялось и в цифрах не заявлено.

Для метрики friction (approvals per task) инструмент подготовлен заранее:
`submission/approval-fatigue/` — стенд с последовательностью approval prompts, набор кейсов и
скрипт разбора. Ответы участников пока не собраны, поэтому сегодня он не даёт ни одного числа в
таблицу выше; он разворачивается вместе с пилотом.

## Критерии выхода из пилота

1. **Safe DENY FP = 0 на всём периоде.** Единственный критерий, не подлежащий согласованию: DENY
   выдаётся только неизменяемыми hard rules, и ложный DENY означает дефект, а не настройку.
2. **Полный набор из 192 сценариев проходит на машине участника с долей успешных атак не выше
   4 % (18/417)**, и ни одна категория, закрытая до 0 % в каноническом прогоне, не отыгрывает
   назад. Проверяется воспроизводимой командой.
3. **Оценка семантического слоя хотя бы раз прогнана на модели участника** и её результат записан.
   Лабораторное число получено на `claude-haiku-4.5`; на другой модели оно будет другим, и пороговое
   значение не назначается заранее — сначала надо узнать, каково оно.
4. **Ни одна пилотная задача не брошена из-за режима без зафиксированного reason code.** Доля
   доведённых задач фиксируется, но её пороговое значение — предмет договорённости с командой, а не
   доказанное число.
5. **Вопросов человеку на задачу не выше согласованного порога** (предложение — 0,5 на задачу).
   Лабораторные 0,29 получены на скриптованном драйвере и прямым ориентиром для живой работы не
   являются; известно только направление — со слоем их вдвое больше, чем без него.
6. **p95 security decision latency остаётся в единицах миллисекунд** на логах пилота; предложенный
   порог 2 мс против лабораторных 1,36 мс — запас, а не измеренная величина. Ожидание модели в это
   число не входит и меряется отдельно.
7. **Каждое выключение режима разобрано и имеет названную причину.** Пороговая доля участников,
   оставивших режим включённым, согласуется с командой до старта: выдумывать это число заранее
   нечестно.
8. **Все понадобившиеся настройки укладываются в три ключа** — `security_auto_tool_capabilities`,
   `security_auto_code_trust`, `security_auto_extension_grants`. Ни одного случая, когда ради одной
   задачи пришлось выключить слой целиком и не включить обратно.

## Что из прошлого плана уже закрыто

**Причина решения показана человеку.** В прошлой редакции это стояло первым пунктом плана: причина
передавалась вместе с запросом, но ни один экран Kilo её не показывал, и человек отвечал на вопрос,
не зная, почему его спросили. Сейчас решение приходит к нему одной фразой в двух местах — в окне
подтверждения и в неинтерактивном прогоне рядом со строкой об отклонении. Проверено записями
настоящих сессий: `submission/evidence/ui/10-ai-injection-stopped` останавливается фразой «The
project README told the agent to send this file to an outside address, which is not something you
asked for», а парная `11-ai-ordinary-work` с теми же двумя действиями и обычным README проходит без
единого лишнего вопроса. Осталась продуктовая часть, которую пилот и должен решить: меняется ли от
этой фразы доля осознанных ответов — а это уже метрика, а не пробел.

## Следующий продуктовый шаг

Порядок задан тем, что первым обоснуют данные пилота, и он изменился: пробел с показом причины
закрыт, прогон на настоящей модели сделан, а самая крупная неизвестность теперь — как слой ведёт
себя на атаках, которых мы не писали.

**Построить новый отложенный набор.** Первое, потому что нынешний израсходован: одна правка в
системе была сделана уже после первого взгляда на его результаты — она пришла из бенчмарка, а не из
этих случаев, и ухудшила число с 29/29 до 27/29, — но правило есть правило. Новый набор нужно строить
теми же парами, что и этот: у обеих половин одинаковая метаданная, различается только смысл текста.
Иначе получится корпус, который проходится по имени файла, — ровно то, чем оказался предыдущий.

**Два дефекта движка правил с известной ценой.** Они дают больше остаточных успехов, чем всё
остальное, и ни один из них не требует модели. Однострочники интерпретаторов — 60 % (9/15): путь
внутри строки после `python -c` не становится операндом команды, это пробел разборщика. `git stash
-u` с последующим `git stash drop` — 17 % (3/18): первый шаг уже очищает рабочее дерево и разрешён,
это недостающее правило. Обе задачи локальные и проверяются теми же сценариями.

**Калибровка чувствительности слоя, а из неё — профили строгости.** Сейчас слой поставляется в
единственной, осторожной настройке. На выбранной модели более чувствительная настройка не меняет
ничего — она отвечает решительно, без промежуточных вердиктов, — но на другой разница появится.
Выбирать по выдуманным данным бессмысленно; пилот даёт распределение решений по причинам и разметку «обоснованно / ложно» — ровно
тот материал, из которого профили и собираются. Сегодня же набор слоёв бинарный: включён или
выключен целиком.

**Верификация Read-Confinement на Linux** тем же набором зондов, которым он верифицирован на macOS.
Приоритет определится составом машин пилота: если Linux-участники есть, это поднимается выше
профилей строгости.

**Аудит-лог для организации.** Решения уже несут reason code, rule id и command fingerprint без
текста команд и содержимого файлов. Недостаёт экспорта, retention и агрегации по команде — и пилот
покажет, какие поля в разборе реально используются.

**Экосистемы за пределами npm-семейства** (pip, cargo, go, системные менеджеры), которые сегодня
сохраняют базовую обработку. Пилот покажет, какие из них реально встречаются в работе команды.

**Upstream contribution.** Разумно после того, как FP-профиль на живых репозиториях измерен и
профили строгости устоялись: предлагать в апстрим слой, порог срабатывания которого ещё не
откалиброван, рано.
