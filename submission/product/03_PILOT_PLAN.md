# План пилота

Security Auto Mode измерен в лаборатории: 130 сценариев (81 attack + 49 utility) × 3 повтора ×
9 конфигураций = 3510 прогонов, 0 errored; ASR снижается со **100 % (237/237)** до **6 % (15/237)**
при utility **98 % (144/147)**. Пилот отвечает на другой вопрос — во что режим обходится живой
команде на настоящем репозитории.

Режим выключен по умолчанию и включается только глобальным конфигом пользователя. Это делает пилот
обратимым: одна строка выключает режим и возвращает прежнее поведение запросов, наборов правил и
загрузки без изменений.

## Кто пилотирует

Команда из 5–10 разработчиков, уже работающая с Kilo Code в автономном режиме, на репозитории с
внешними зависимостями и подключёнными MCP-инструментами. Плюс один engineering/security lead как
владелец решения.

Профиль выбран под то, что осталось неизмеренным. Лаборатория меряет containment на скриптованных
траекториях; она не меряет, как часто на реальном коде срабатывают эвристические поверхности —
Package Security (adoption, схожесть имени, возраст) и Content Secret Detection (именованные
детекторы). False-positive профиль на настоящих репозиториях можно получить только на живой работе.

Нужен именно автономный режим: hard ASK не снимается ни `--auto`, ни сохранённым «always allow», ни
неинтерактивным ответом. Команда, которая и так подтверждает каждое действие руками, не почувствует
разницы и не даст сигнала о friction.

Владелец решения нужен потому, что три настройки — `security_auto_tool_capabilities`,
`security_auto_code_trust`, `security_auto_extension_grants` — по замыслу лежат выше уровня проекта:
репозиторий не может ни выдать capability, ни одобрить код. Кто-то должен принимать эти решения
осознанно.

Больший rollout преждевременен по трём причинам. Read-Confinement верифицирован на macOS, для Linux
реализован, но здесь не верифицирован. Пять остаточных сценариев остаются на 100 % и требуют явного
проговаривания с каждым участником. И порог friction, приемлемый для команды, пока не установлен —
его как раз и предстоит измерить.

## Сценарий пилота

1. **Включение.** Владелец решения раскладывает участникам глобальный конфиг:
   `{ "experimental": { "security_auto": true } }` (или `KILO_SECURITY_AUTO=1`). Проектный конфиг в
   этом не участвует и не может ничего переопределить.
2. **Дефолтный набор слоёв.** Все шесть переключаемых слоёв — Package Security, Stateful Egress,
   Delegated Tool Security, Content Secret Detection, Executable Code Trust, Permissioned Extension
   Runtime — включаются вместе с режимом. Read-Confinement активен, потому что
   `security_auto_extension_unconfined_reads` по умолчанию выключен. Ничего донастраивать на старте
   не требуется.
3. **Что видит пользователь.** ALLOW проходит как раньше. Hard ASK — интерактивный запрос, на
   который должен ответить человек. DENY — завершённый tool result «Blocked by security policy» со
   стабильным reason code, человекочитаемой причиной, `canRetry` и безопасными альтернативами; ход
   продолжается, работа не обрывается.
4. **Инструменты команды.** Для своих MCP-серверов владелец заводит декларации в
   `security_auto_tool_capabilities` (`readonly`, `network`, `filesystem-write`, …). Без декларации
   инструмент — unknown authority и получает hard ASK на каждый вызов; `process` и
   `security-control` не делегируются unattended by design.
5. **Репозиторный исполняемый код.** Если в проекте есть `.kilocode/tool/*.ts` или объявленный
   плагин, он обнаруживается, но не импортируется. В блоке приходит готовая строка вида
   «Add "<sha256>" to experimental.security_auto_code_trust in your global Kilo config». Одобрение —
   действие человека в его собственном конфиге, по содержимому: правка файла отзывает его.
6. **Расширения.** Одобренное workspace-расширение по умолчанию получает только `filesystem-read`;
   всё остальное выдаётся точечно через `security_auto_extension_grants` на конкретный digest.
7. **Обратная связь.** Основной канал — сами решения: логи несут reason code, rule id и command
   fingerprint, но никогда текст команды и содержимое файлов. Владелец еженедельно разбирает список
   hard ASK и DENY по reason code и список заблокированных кандидатов на загрузку, размечая каждое
   как обоснованное или ложное. Это и есть измерение FP.
8. **Контрольная точка.** В начале и в конце периода бенчмарк прогоняется на машине участника
   воспроизводимой командой из документации — чтобы отличить регрессию платформы от особенностей
   репозитория.

## Метрики успеха

Лабораторные значения и пилотные — **разные знаменатели и разные измерения**. В лаборатории
знаменатель ASR — 237 прогонов атак скриптованного драйвера в одноразовом sandbox, утилиты —
147 прогонов; успех атаки там наблюдаемый побочный эффект, а не текст модели. В пилоте знаменатель —
реальные задачи живых людей на настоящих репозиториях, где никто атак не подкладывает. Числа из
двух колонок ниже нельзя ставить рядом как «было / стало».

| Метрика | Как измеряется в пилоте | Текущее значение на benchmark | Порог для пилота |
|---|---|---|---|
| ASR | Только на контролируемом наборе сценариев, прогоняемом на машине участника. По проду ASR не считается: там нет оракула побочного эффекта | **6 % (15/237)** | Не выше лабораторного; ни одна категория, закрытая до 0 % в каноническом прогоне (SOURCE_OF_TRUTH §7), не отыгрывает назад |
| Task Utility | Доля пилотных задач, доведённых до конца без выключения режима и без обхода политики | **98 % (144/147)**; extension + executable-code 100 % (42/42); content 100 % (27/27) | Согласуется с командой до старта; предложение — не ниже 95 % |
| Safe DENY FP / Safe ASK FP | Ручная разметка владельцем: каждое DENY и hard ASK помечается как обоснованное или ложное | Safe DENY FP = **0**; Safe ASK FP = 6 | DENY FP = 0 весь период — жёсткий критерий. Порог по ASK FP согласуется |
| Approvals per task | Число интерактивных ответов на hard ASK, делённое на число задач | ASK/task **0,154**; DENY/task 0,30 | Предложение, а не доказанное значение: не выше 0,5 на задачу |
| End-to-end latency | Воспринимаемая задержка сессии; отдельно — холодный старт extension host | Task latency 15,3 → 17,2 мс (конфаундед); холодный старт 22,9 мс p50 confined против 21,9 мс open | Отсутствие воспринимаемой регрессии; рост холодного старта в пределах единиц миллисекунд |
| Security decision latency | Тот же seam наблюдения за решениями, что и в бенчмарке | p50 **0,65 мс** / p95 **1,04 мс** | Предложение: p95 не выше 2 мс на логах пилота |
| Доверие пользователя | Доля участников с включённым режимом на конец периода; каждое выключение фиксируется с причиной | Лабораторного эквивалента нет | Порог согласуется с командой до старта; сам факт выключения разбирается всегда |

Task latency отмечена как конфаундед намеренно: заблокированная атака не делает работу, поэтому
средняя задержка задачи в лаборатории сравнивает неравные объёмы работы. Единственная честная
латентность здесь — стоимость решения политики.

Для метрики friction (approvals per task) инструмент подготовлен заранее:
`submission/approval-fatigue/` — стенд с последовательностью approval prompts, набор кейсов и
скрипт разбора. Ответы участников пока не собраны, поэтому сегодня он не даёт ни одного числа в
таблицу выше; он разворачивается вместе с пилотом.

## Риски пилота

| Риск | Как проявится | Митигация | Кто отвечает |
|---|---|---|---|
| False positives | Безопасное действие уходит в hard ASK. Измеренный пример: честный трёхдневный пакет (`util-package-install-safe-new`) получает hard ASK, и автономный клиент не может ответить | Каждый слой выключается отдельно глобальным ключом или env; capability-декларации снимают класс сразу; разметка по reason code показывает, какой именно слой шумит | Security lead |
| Различия sandbox между платформами | macOS — верифицирован. Linux — реализован, но здесь не верифицирован. Windows и платформы без backend: одобренное workspace-расширение не запускается, пока пользователь явно не выставит `security_auto_extension_unconfined_reads` | Основной контур пилота — macOS. Участники на Linux прогоняют набор зондов перед стартом. На Windows расширения выводятся из scope пилота, остальные слои работают | Владелец решения |
| Новые tool capabilities | Подключённый в середине пилота MCP-инструмент без декларации — unknown authority и hard ASK на каждый вызов | Декларации заводятся тем же действием, что и подключение сервера; `process` и `security-control` остаются недоступны для unattended-делегирования by design | Security lead |
| Недоступность package metadata | Реестр недоступен — lookup failure никогда не сводится к ALLOW, установки начинают спрашивать | Живой адаптер работает с таймаутом, ограничением размера и кешем. При системном сбое реестра `security_auto_packages` временно выключается глобально, остальные слои остаются | Владелец решения |
| Потеря доверия пользователя | Участник выключает режим целиком вместо точечной настройки | Каждый блок несёт причину и безопасные альтернативы, а не молчаливый отказ. Еженедельный разбор; каждое выключение фиксируется как сигнал, а не как нарушение | Engineering lead |
| Сложность политики | Три ключа настройки воспринимаются как отдельная система конфигурации | Дефолт — не настраивать ничего. Строка одобрения кода выдаётся готовой в самом блоке. Настройки централизованы у одного владельца, а не размазаны по участникам | Владелец решения |
| Остаточные атаки | Пять сценариев остаются на 100 %: `atk-extread-metadata-probe`, `atk-pregate-plugin-hook`, `atk-content-bare-token-residual`, `atk-content-encoded-residual`, `atk-readme-injection-exfil`. Участник может прочитать «включено» как «защищено» | Список остаточных классов проговаривается на старте письменно: семантический prompt injection через текст и немаркированные секреты вне scope архитектуры; defense in depth, а не гарантия | Security lead |

## Критерии выхода из пилота

1. **Safe DENY FP = 0 на всём периоде.** Единственный критерий, не подлежащий согласованию: DENY
   выдаётся только неизменяемыми hard rules, и ложный DENY означает дефект, а не настройку.
2. **Полный набор из 130 сценариев проходит на машине участника с ASR не выше 6 % (15/237)**, и ни
   одна категория, закрытая до 0 % в каноническом прогоне (SOURCE_OF_TRUTH §7), не отыгрывает
   назад. Проверяется воспроизводимой командой.
3. **Ни одна пилотная задача не брошена из-за режима без зафиксированного reason code.** Доля
   доведённых задач фиксируется, но её пороговое значение — предмет договорённости с командой, а не
   доказанное число.
4. **Approvals per task не выше согласованного порога** (предложение — 0,5 на задачу). Лабораторное
   ASK/task 0,154 получено на скриптованном драйвере и прямым ориентиром для живой работы не
   является.
5. **p95 security decision latency остаётся в единицах миллисекунд** на логах пилота; предложенный
   порог 2 мс против лабораторных 1,04 мс — запас, а не измеренная величина.
6. **Каждое выключение режима разобрано и имеет названную причину.** Пороговая доля участников,
   оставивших режим включённым, согласуется с командой до старта: выдумывать это число заранее
   нечестно.
7. **Все понадобившиеся настройки укладываются в три ключа** — `security_auto_tool_capabilities`,
   `security_auto_code_trust`, `security_auto_extension_grants`. Ни одного случая, когда ради одной
   задачи пришлось выключить слой целиком и не включить обратно.

## Следующий продуктовый шаг

Порядок задан тем, что первым обоснуют данные пилота.

**Показать причину решения в самом окне подтверждения.** Это первое, потому что это не гипотеза, а
измеренный пробел: причина решения уже передаётся вместе с запросом (`metadata.security` —
`reasonCode`, сработавшие правила, безопасные замены), но ни один экран Kilo её сегодня не
показывает. Проверено записями настоящих сессий в `submission/evidence/ui/`: в окне подтверждения
человек видит только команду, а полный текст с причиной получает агент — в результате инструмента.
Из-за этого человек отвечает на вопрос, не зная, почему его спросили; это ровно та ситуация, из
которой растёт привычка нажимать «разрешить» не глядя. Работы здесь мало — данные уже есть в
запросе, — а эффект на доверие к режиму прямой, и пилот сразу покажет, меняется ли доля
подтверждений.

**Профили строгости (осторожный / обычный / свободный).** Пилот даёт распределение решений по
причинам и разметку «обоснованно / ложно» — ровно тот материал, из которого собираются профили.
Сегодня набор слоёв бинарный: включён или выключен целиком.

**Аудит-лог для организации.** Решения уже несут reason code, rule id и command fingerprint без
текста команд и содержимого файлов. Недостаёт экспорта, retention и агрегации по команде — и пилот
покажет, какие поля в разборе реально используются.

**Верификация Read-Confinement на Linux** тем же набором зондов, которым он верифицирован на macOS.
Приоритет определится составом машин пилота: если Linux-участники есть, это поднимается выше
профилей риска.

**Экосистемы за пределами npm-семейства** (pip, cargo, go, системные менеджеры), которые сегодня
сохраняют базовую обработку. Пилот покажет, какие из них реально встречаются в работе команды.

**Upstream contribution.** Разумно после того, как FP-профиль на живых репозиториях измерен и
профили риска устоялись: предлагать в апстрим слой, порог срабатывания которого ещё не откалиброван,
рано.
