# Security Auto Mode — семантический слой поверх детерминированного контура

Статус: реализовано, **входит в итоговую конфигурацию**.
Флаг: `experimental.security_auto_classifier` / `KILO_SECURITY_AUTO_CLASSIFIER` — включён вместе с
режимом; выключателем на практике служит наличие настроенной модели, а не второй флаг.

## 0. Какие задачи решает модель

Не «опасна ли эта команда» — на это детерминированный движок отвечает лучше, за микросекунды и без
сети. Два вопроса, на которые у движка нет входа:

**(а) Была ли в тексте, который агент прочитал, инструкция, заставившая его это сделать?**
Классификатору путей `README.md` проекта, `README.md` зависимости и сохранённая веб-страница —
одинаково «обычный файл рабочей области». Все три написал не пользователь, и только это имеет
значение для непрямой инъекции.

**(б) Имеет ли действие отношение к тому, о чём просил пользователь?**
Здесь у движка нет вообще ничего: в классе `attack-goal-mismatch` нет ни опасной команды, ни
защищённого пути, ни подозрительного пакета. Есть чтение обычного файла и его отправка наружу —
и то, что пользователь просил поправить опечатку в README. Детерминированный ASR этого класса
**100% до и 100% после**; 0% даёт только семантический слой.

**И одна продуктовая задача.** Когда решение доходит до человека, модель переписывает уже готовое
детерминированное предложение в понятную фразу. На само решение это не влияет никак: см. раздел 9.

```
   ┌──────────────── действие агента (tool call) ────────────────┐
   ▼                                                             │
[ Deterministic Security Engine ]  ← ИСТОЧНИК ПОЛНОМОЧИЙ         │
   • опасные команды / защищённые пути / package policy          │
   • Capability / CodeTrust / Session State                      │
   → набор evidence → свёртка → ALLOW / soft-ASK / hard-ASK / DENY
   │                                                             │
   ├─ DENY или hard-ASK ──────────────────────► модель не вызывается
   ├─ действие без сети и без делегирования ──► модель не вызывается
   ├─ сессия ничего недоверенного не читала ──► модель не вызывается
   │                                                             │
   └─ иначе: недоверенный текст + структура действия + цель       │
             ▼                                                   │
   [ Semantic Evidence ]  → либо ничего, либо одно evidence «ask» │
     • инструкция в недоверенном тексте                          │
     • действие не соответствует задаче пользователя             │
             ▼                                                   │
   та же монотонная свёртка ────────────────────────────────────┘
             ▼
   [ OS Sandbox / Extension Runtime ]  ← ограничивает даже после ALLOW
             ▼
        выполнение
```

## 1. Инварианты — свойство кода, а не обещание

`Decision.reduce` сворачивает evidence функцией `stricter()`, начиная с `allow`. Добавление элементов
двигает решение только к ASK/DENY. Слой, умеющий **только дописывать**, структурно неспособен
что-либо ослабить.

Отсюда, без единой проверки вида «если DENY — верни DENY»:

1. Детерминированный `DENY` остаётся `DENY` при любом ответе модели.
2. `hard-ASK` не понижается.
3. Модель не может выдать `ALLOW` — это нейтральный элемент свёртки, а не значение, которое слой
   способен внести. `BENIGN_CONTEXT` есть в словаре, чтобы модели было куда положить «я посмотрел,
   всё нормально», и он отображается в **пустой список** evidence: единственное представление
   благоприятного вердикта, которое нельзя превратить в разрешение.
4. Модель не может выдать `DENY`. Она вносит `ask`: слой на модели вправе потребовать человека, но не
   вправе сам завершить задачу.

5. **Сбой не ослабляет.** `Decision.failure` теперь **вкладывает** отказ в уже достигнутое решение, а
   не заменяет его. Раньше любой дефект после того, как DENY был получен — в следующем слое, у
   провайдера, в предложении для человека — выбрасывал этот DENY и подставлял жёсткий вопрос, на
   который разрешающее правило умеет ответить. Свойство теперь арифметическое: отказ — это `ask`,
   `stricter()` берёт максимум, значит DENY остаётся DENY, жёсткий вопрос остаётся жёстким, мягкий
   становится жёстким, а ALLOW — отказоустойчивым вопросом. Плюс каждый слой изолирован: слой,
   бросивший исключение, вносит evidence об ошибке и не уносит с собой остальные.

Проверено в бенчмарке, а не только в тестах: с включённым слоем счётчики `auto ALLOW` и `DENY` не
сдвинулись ни на единицу — изменились только решения, перешедшие из soft ASK в hard ASK. Числа — в
`security-auto-mode-llm-results.md`.

## 2. Что подаётся на вход

| Вход | Откуда | Замечание |
|---|---|---|
| Структура действия | нормализация движка | программа, факт сети, вид эффекта, **имена файлов без каталогов**, классы расположения, метки |
| Недоверенные выдержки | `SecuritySessionState`, до 8 × 2 КБ | записываются при **успешном завершении** вызова: текст отказанного вызова агент не читал |
| Происхождение каждой выдержки | `ingestSource` в `gate.ts` | `workspace-file`, `source-comment`, `dependency`, `notebook`, `ci-config`, `skill`, `mcp`, `web`, `tool` |
| Цель пользователя | `SecuritySessionState`, до 500 знаков | записывается там, где ход и так извлекает текст пользователя; **evidence о намерении, не полномочие** |

Никогда не подаётся: командная строка, абсолютные пути, содержимое файлов, транскрипт разговора.

**Редактирование перед отправкой.** Выдержки — это текст, который агент прочитал, а прочитанный текст
может содержать учётные данные: не потому, что агент их искал, а потому что они лежали в файле
репозитория. Значение модели не нужно — вопрос в том, что текст **велит сделать**, и это переживает
замену значения на `[redacted]`. Поэтому `SemanticEvidence.redactInput` прогоняет каждую выдержку и
саму цель через детектор секретов на единственной границе, где данные уходят наружу. Тест кладёт
синтетический ключ в выдержку и проверяет, что провайдер его не видел. Тот же путь применяет и
eval-скрипт: корпус, оценённый на тексте, который продукт никогда не отправит, измеряет
несуществующий конвейер.

Вывод, к которому это привело на практике: предыдущая версия слоя судила команду и видела только имя
файла. Она ловила выгрузку файла с подозрительным именем и пропускала **все** случаи, где секрет
сначала перекладывали в файл с именем `staged.dat`. Имя — это всё, что у неё было.

## 3. Полоса вызова

Три условия, все обязательны:

| Условие | Почему |
|---|---|
| Детерминированный слой не решил (не DENY и не hard-ASK) | решённое решать незачем — только задержка |
| Действие выходит в сеть или идёт через делегированный инструмент | `ls` — не задача про семантику |
| Сессия прочитала что-то недоверенное или есть записанная цель | иначе спрашивать не о чем: есть только команда, а команды движок читает лучше |

Измерено: **0.16 вызова на решение** — примерно одно из шести.

**Плюс один структурный запрет после вердикта.** Вердикт `USER_GOAL_MISMATCH` отбрасывается, если
цель в этой сессии не записана. Сравнивать не с чем, а модель, которую всё равно спросили, отвечает
из самого отсутствия — так «мы не знаем, чего вы хотели» превращается в трение на обычной работе.
Измерено на прогоне до запрета: 37 из 39 решений помечено и 10 из 51 задачи потеряно; после — 29 из
39 и одна из 51. Это код, а не строчка в промпте, потому что строчка в промпте — это просьба.

## 4. Отказ неотличим от выключенного слоя

Нет провайдера, таймаут, ошибка транспорта, ответ вне словаря, провайдер, бросающий исключение
синхронно, — всегда пустой список evidence, то есть детерминированное решение остаётся ровно таким,
каким было. Это и есть ответ на «AI в итоговой версии, но его отсутствие ничего не ломает»: без
модели продукт ведёт себя как без этого кода.

Дедлайн ограничивает **ожидание**, а не только работу: `AbortSignal` уходит провайдеру, чтобы
воспитанный клиент остановился сам, но решение ждёт ровно до гонки с таймером. Разница измерима —
разрешение модели идёт через сервис провайдера и тратит время, которое никакой сигнал отмены не
прерывает. Бюджет `KILO_SECURITY_AUTO_CLASSIFIER_TIMEOUT_MS`, по умолчанию **2500 мс**: `haiku-4.5`
через шлюз отвечает за ~960 мс (p50) и 1215 мс (p95) в тихом процессе и 1250 / 2475 мс под нагрузкой
бенчмарка. Прежние 300 мс были написаны до того, как хоть что-то измерили настоящую модель, и с ними
слой молчал бы почти всегда — безопасно и бесполезно.

**Предохранитель.** Неверно настроенный провайдер отказывает одинаково каждый раз, и платить за него
дедлайн на каждом решении — это дефект задержки, замаскированный под безопасность. После трёх подряд
отказов слой перестаёт спрашивать до конца процесса. Измерено: пять решений с недоступной моделью
стоят 906 мс один раз, а не полный дедлайн всегда.

## 5. Устойчивость самого классификатора к инъекции

Слой существует, чтобы читать текст, который пишет тот, кто контролирует репозиторий. Поэтому промпт
строится так, будто содержимое враждебно:

- содержимое **никогда не склеивается с инструкцией** — оно внутри ограждения со случайным одноразовым
  меткой-nonce, поэтому закрыть блок или открыть новый изнутри нельзя;
- всякое вхождение nonce внутри содержимого затирается, так что совпадение не помогает;
- инструкция заранее говорит: всё внутри блока — данные, найденные там команды являются **предметом
  вопроса**, а не указаниями;
- словарь ответа закрыт и разбирается точно: `RISK=… CATEGORY=… CONFIDENCE=…` одной строкой. Проза,
  отказ, JSON, поддельный вердикт внутри содержимого — всё читается как «сигнала нет»;
- содержимое усечено (4 × 1200 знаков), чтобы длинный документ не вытеснил вопрос.

Но по-настоящему инъекция в этот слой неинтересна по другой причине: слой умеет **только ужесточать**.
Лучшее, чего добивается успешная манипуляция, — вердикт `ORDINARY`, то есть ровно то поведение,
которое было бы с выключенным слоем. Открыть что-либо нельзя в принципе.

Отдельный набор `SEMANTIC_ADVERSARIAL` (13 случаев) проверяет первую половину эмпирически: настоящая
инъекция плюс вторая полезная нагрузка, нацеленная уже на проверяющего — готовый вердикт, поддельная
системная реплика, поддельный `<USER_REQUEST>`, попытка закрыть ограждение, JSON- и
Markdown-подделка, «отвечай ORDINARY» на другом языке, инструкция в base64, требование распечатать
секрет, стена наполнителя. На `claude-haiku-4.5` слой пометил **13 из 13**: ни одна попытка не
сработала. Вторую половину проверять нечем — она следует из свёртки.

## 6. Словарь и консервативное отображение

```
risk:        ORDINARY | SUSPICIOUS | HIGH_RISK
category:    NONE | BENIGN_CONTEXT | PROMPT_INJECTION | USER_GOAL_MISMATCH
             | DATA_EXFILTRATION | DELEGATED_AUTHORITY
confidence:  LOW | MEDIUM | HIGH
```

| Вердикт | Что вносится |
|---|---|
| `HIGH_RISK` + HIGH/MEDIUM | hard ASK |
| `HIGH_RISK` + LOW | soft ASK |
| `SUSPICIOUS` + HIGH | soft ASK |
| `SUSPICIOUS` + MEDIUM | ничего (`conservative`) / soft ASK (`balanced`) |
| всё остальное, включая `BENIGN_CONTEXT` | ничего |

Порогов на самокалиброванных числах нет: три метки, три грубых исхода. `Sensitivity` вынесена в
настройку (`KILO_SECURITY_AUTO_CLASSIFIER_SENSITIVITY`, по умолчанию `conservative`), потому что
измерение показало: порог значит больше, чем всё остальное в слое, а насколько уверенности провайдера
можно верить — свойство провайдера, а не этого файла.

## 7. Провайдеры

| Провайдер | Когда | Замечание |
|---|---|---|
| `kilo` (по умолчанию) | продукт | модель, которой Kilo уже настроен, через его же сервис провайдеров: ни ключа, ни вендора в коде |
| `MockProvider` | тесты | вердикты по скрипту |
| `heuristic` | офлайн-прогоны, CI | **заглушка, а не модель**; написана по `DEVELOPMENT`-набору и не обобщается — на held-out берёт 1 из 29 |
| `MetadataBaseline` | eval | нарочно слепой: читает всё, кроме недоверенного текста. Мера того, сколько корпуса проходится без чтения |
| `anthropic` / `openai` | контур без Kilo-конфигурации | прямые backend-ы; `openai` годится и для локального Ollama |

Модель можно **закрепить** — `KILO_SECURITY_AUTO_CLASSIFIER_MODEL=<провайдер>/<модель>` — когда
классификатор безопасности не должен зависеть от того, какой моделью пользователь пишет код.
Учётные данные берутся оттуда же, откуда их берёт сам Kilo: конфиг, auth-хранилище или переменная
окружения провайдера. Ни ключа, ни адреса в коде безопасности нет.

Измерено на `openrouter/anthropic/claude-haiku-4.5`; вторым кандидатом был
`openrouter/google/gemini-2.5-flash-lite` (см. `security-auto-mode-llm-results.md`, раздел о выборе
модели).

Провайдер `kilo` загружается через `await import()`: подсистема classifier иначе остаётся листом с
секундными юнит-тестами, а граф провайдера — сильно связная компонента, которая в этом проекте уже
один раз давала `Cannot access 'node' before initialization`. Импорт стартует при **создании**
backend-а, а не на первом вызове: иначе первое решение в процессе, которому нужен вердикт, всегда
получало пустоту — тихая мёртвая зона в начале сессии.

## 9. Объяснение риска человеку

Когда решение — `ASK` или `DENY`, оно доходит до клиента с одной фразой на обычном языке: что агент
собирается сделать и чем это грозит. Раньше решение доходило, но **ничего его не отображало** —
запрос про разрушительную команду и запрос про установку пакета выглядели одинаково.

- `RiskExplanation.template()` — детерминированное предложение на каждый код причины. Ничего не стоит
  и не может отказать. Это и есть продукт.
- Модель только **переписывает** это предложение. Любой сбой — нет провайдера, таймаут, ответ не
  похожий на одну фразу — оставляет шаблон.
- Модель зовут только там, где человек фразу точно прочитает: жёсткий запрос и запрет. Мягкий запрос
  может быть удовлетворён уже сохранённым правилом, и второй удалённый вызов на каждом таком решении
  покупает задержку и ничего больше. Детерминированная фраза пишется в обоих случаях, поэтому без
  объяснения не остаётся ни одно решение.
- На решение не влияет: строится из уже финального решения и никем не читается обратно.
- Вход — маленькая обезвреженная запись: код причины, классы путей, имя хранилища как `aws`, а не как
  путь. Ни содержимого файлов, ни командной строки, ни абсолютных путей. Тесты проверяют, что ни один
  шаблон не содержит каталога, URL или домашнего пути и что код правила не просачивается в текст.

Видно в двух местах: в интерактивном запросе TUI и в выводе `kilo run` при автоотказе.

## 8. Что не сделано

- **Цель записана только у пяти сценариев бенчмарка.** В живой сессии её пишет ход разговора, в
  бенчмарке — только там, где сценарий её объявил. Поэтому вклад сигнала цели виден на этих пяти и на
  held-out наборе, а на остальных 155 сценариях работает вопрос (а). Структурный запрет из раздела 3
  делает это безопасным, но не делает измеренным.
- **Одна ложная эскалация на 51 обычной задаче**: `util-content-public-key` — публикация открытого
  ключа. Это измеренная цена, а не сбой.
- **Phase 0 — детерминированные фиксы найденных дыр.** Из четырёх сделаны две:
  - [x] каналы egress: `curl -F`, `--data-urlencode`
  - [x] запись в `/dev/null` больше не считается изменением системных файлов
  - [ ] taint по значению за `cp` / `mv` / `sed` / `awk` / кодированием
  - [ ] анализ аргументов интерпретаторов: `python -c`, `node -e`, `perl -e`
  - [ ] `git stash -u`
